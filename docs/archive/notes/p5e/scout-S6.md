## 3. The gap - knobs, fields, records, rules that do not exist

1. **`IpcTable::RunAhead`** = `MOBILEGL_IPC_RUN_AHEAD` (default 1; forced 0 by `PipeVerify` beside `:377`; meaningless when `VerbBarrier==0`). **`IpcTable::PresentCredit`** = `MOBILEGL_IPC_PRESENT_CREDIT` (default **1**, range 1..8 - see §4(2)).
2. **`kCapRunAheadApply = 1ull << 10`** in `MGPCapBit`; set in the DirectGLES arm of the server's `CallMask`, never in the Magma arm. Client predicate `ClientSession::RunAheadArmed()` = `m_barrierArmed && Ipc.RunAhead && Caps().HasCap(kCapRunAheadApply)`, latched at the first CapsSnapshot adoption after `Start` (a later snapshot may only turn it OFF - a caps re-run cannot make a lockstep server run-ahead mid-frame).
3. **A wait class per op**, generated beside `kMGPipeCallFlags` (`MGPipeWaitClassFor(op)`): `kWaitReply` (every `kReplySlot` row), `kWaitApplied` (`ApplierReset`, `FenceWaitServer`? - no: GPU-side, fire-and-forget; only `ApplierReset` and `GenerateMipmap` until S2 retires the `GetActiveTextureUnit` read at DirectGLES `GenerateMipmap`, ClientSession.cpp:900-914), `kWaitPresent` (`Present`), `kWaitNone` (everything else, including `ResourceDestroy`, `UnmapPersistent`, `FenceCreate/Destroy`, the five non-reply query rows, all `kCtxVerb` rows but `ReadPixels`/`Present`). Row-level override, not a per-op runtime guess.
4. **`resource_subdata` without a reply for the buffer half.** The row keeps `kReplySlot` on the wire (the server posts; an unread slot is harmless: the client reads a slot only after `appliedSeq >= seq`, and a slot is rewritten only by a record 8 seqs later, ReplySlot.h:16,:105); `Wire_ResourceSubData` (WireTables.cpp:332-352) takes a `wantReply` from the route: `MGPipeRouteResourceSubData` passes `nullptr` for buffers (the Bool at PipeFill.cpp:839 is discarded today) and the texture drain's D-D5 acceptance is a ruling for S2/S8 (see §7). Without this the pmap push stays lockstep.
5. **`MGPPresent::FrameSerial` minted by the client** (`++m_presentsSent`, 1-based); `OnPresent` calls `ServerSession::Active()->ReturnPresentCredit(present.FrameSerial)` after `table->Present()` returns (m-1's 1:1 holds: one credit per swap). Client: `WaitForPresentAck(m_presentsSent - PresentCredit)` BEFORE encoding present N when `m_presentsSent - PresentCredit >= 1`.
6. **`gPipeInputs` client-side skip.** In `MGPipeValidateForVerb`, when `RunAheadArmed()`: skip `:2989`, `:2997`, `:2999-3001`, the whole of step 4 (`:3252-3270`), and `MGPipeLeaveVerb`'s writes; `MGPipeNoteFrontendMutation` returns at `:554`; step 2 (tracker walk) and step 3 (emitters) run unchanged. `VertexAttribDefaultsOf` (:84) must diff against the emitter's own last header (`g_attribDefaultLastHeader`, :2949) - a client mirror, never the block. **One-time release of the four O-class SharedPtr rows** (`PipeInputs.h:801-809` `m_boundVertexArray`, the three programs) at the switch, on the GL thread, or the last lockstep fill pins those objects for the process life and the apply thread can become their last owner. `SetIdentity` (:3001) moves to the server (`ApplyOne` sets it once from its own backend).
7. **Server stamp under run-ahead.** `MGPipeServerStampVerbBoundary(verb, runAhead)`; `MGPipeInputUnfreshRead` under `runAhead` takes `StrictBarrierPullFatal` **regardless of `StrictErrors`** (the value in the row is torn or stale by construction, P5e-3); `CountBarrierPull` stays for lockstep. The sticky forwards (`MGPipeStickyForwardPull` :251-257) are the same: Fatal under a run-ahead verb.
8. **Event-ring flow control** (ARCHITECTURE §11.7 made real): server `Reserve==nullptr` -> latch `eventRingFull` (exists), publish, `NotifyClient`, then park in `ServerLoop::ApplyThreadMain`'s loop with `eventRingFull==0` added to `ready` (:380-383) - NOT `Fatal{EventRingOverflow}` when `RunAheadArmed`; client: every `Park` exit in `ClientSession` (applied, present-ack, cmd-space, and the stage bell at PipeWireCodec.cpp:836, which is the same `SelfDoorbell`) re-checks `m_events.RingIsFull()` and drains before re-parking. Deadlock argument: the server blocks only on the event ring; the client blocks only on watermarks the server advances; the client's every wait drains; so at most one side is parked at any instant.
9. **Deferred destroy under run-ahead**: keep the queue; `MGPipeDeferDestroyAndFreeIfOnApplyThread` under `RunAheadArmed` logs `MGLOG_E_ONCE` with the kind (after S1-S7 the server holds no frontend SharedPtr; an enqueue is a finding) - Fatal in strict.
10. **`RefusePipeInputsTouchWhileApplierOwnsIt`** is re-derived: under run-ahead the rule is "the GL thread never touches the block", so the guard becomes unconditional on the surfaces named in (6) when `RunAheadArmed()` (the `BatchWaits` early return at `:1037` goes; the check no longer consults `ApplyThreadIsInsideApplier`). `Fatal{BarrierViolation}` (:840) stays for `BatchWaits==0 && !RunAhead`.

## 4. The retirement design

**(1) The wait rule.** `EmitAndWaitTails` after `PublishAndNotify`:
```
if (ownsReplySlot)                       -> WaitForAppliedBudget + DrainEventRing + ReadReply   (unchanged)
else if (RunAheadArmed()) switch (MGPipeWaitClassFor(op)) {
    kWaitNone:    return seq;
    kWaitApplied: WaitForAppliedBudget + DrainEventRing; return seq;        // applier_reset, generate_mipmap (until S2)
    kWaitPresent: (credit wait happens in EmitPresent BEFORE encode; here: return seq) }
else                                     -> today's :915-959 shape, byte for byte
```
`VerbBarrier==0` keeps its meaning (nothing but reply rows waits) and stays the R-1 negative control for the lockstep arm; under run-ahead its expected red is `applier_reset` ordering (`Fatal{ProtocolCorruption,"ApplierReset.ContextSerial"}` cannot fire - the ring orders it - so the control has to be re-pointed at the strict detector: §6). Magma: `kCapRunAheadApply` absent -> `RunAheadArmed()==false` -> today's path; the negative control for the switch is `MOBILEGL_IPC_RUN_AHEAD=1` on Magma, which must log "run-ahead requested, server does not publish kCapRunAheadApply" and run lockstep.

**(2) Present pacing.** `EmitPresent`: `BeforeReadOnlyVerb(); if (m_presentsSent >= credit) WaitForPresentAck(m_presentsSent + 1 - credit, 30 s) [ShutDown -> return; TimedOut -> Fatal{PresentCreditTimeout}]; DrainEventRing; encode/publish; PumpControlPlane`. With credit 1 the client publishes frame N+1's records while the server applies and swaps frame N and blocks at present N+1 until swap N returned - one full frame of overlap, the shape ARCHITECTURE §14 defaults to; credit 2 adds one frame of end-to-end latency for no CPU gain on a CPU-bound client. **Default 1.** Ring budget at ~850 draws + ~0.36 MB pmap/frame: SEG_CMD in flight per frame is ~68 KB of draws + the set/CSO records (bounded by the same frame) - well under 1 MiB, so 8 MiB holds 8+ frames; SEG_STAGE at 0.36 MB/frame + subdata/texture blobs holds 32 MiB / ~1 MB = ~30 frames; SEG_REPLY unchanged (reply rows still one deep). Backpressure is therefore the present credit, never the bytes; `WaitForCmdSpace`/the stage bell are the safety net and both must drain events on exit (§3(8)).

**(3) Drains and forced waits.** Drain points: every wait exit (reply rows, present credit, cmd-space, stage), the four RPC sites, and `Stop`. Client operations that force a wait: `MapBuffer(READ)` / `GetBufferSubData` / `CopyBufferSubData` source -> `SyncGpuWrites` (reply row, unchanged); `glFinish` -> emits `Flush`? No: `Flush`/`Finish` stay no-ops on the wire (ARCHITECTURE:415); `glFinish` under run-ahead = `WaitForApplied(LastPublishedSeq)` + drain, spelled in the client `Finish` slot (new, one line); `glClientWaitSync` / `GetSyncStatus` / `QueryAvailable` / `QueryResult` are reply rows (wait); `glGetError`: **the relaxation** - server-side GL errors (`kEventGlError`, DirectGLES.cpp:8804 -> ServerSession.cpp:634-666) are observed at the next drain, so `glGetError` reports a run-ahead verb's error at or after the next wait point rather than at the call after it; CONTRACT-P5C §4.2 already assigns the ordering to P9; P5e names the window as "<= one present credit". `eglMakeCurrent` / surface RPCs: `RunOnApplyThread` already serialises with the ring? NO - the mailbox is pumped between `DrainRing` batches (ServerLoop.cpp:385-390), so a make-current can land between two run-ahead records. Rule: the client waits `WaitForApplied(LastPublishedSeq)` before every `Server*` EGL forwarder (BackendObject_Remote.cpp) - the "control records that need it" of P5e-2; `applier_reset` is the same, it is a `kWaitApplied` row.

**(4) `gPipeInputs` ownership.** Under a live wire and `RunAheadArmed()` the block is server-role memory: the client executes steps 2 and 3 of `MGPipeValidateForVerb` and nothing else; the server stamps at `ApplyOne` (unchanged), `SetIdentity` once per session; the detector is (§3(7)); the verify build forces `RunAhead=0` (comparator needs a client-filled block, PipeFill.cpp:3304). The residual-value trip wire (`:3284-3294`) still emits - it compares on the SERVER against the applier-derived mirror, which is the honest half. The `MGP_FILL` call sites (GL_Drawing.cpp:540-640) do not change.

**(5) Object lifetime.** ABA: the client frees a slot right after emitting the destroy (PipeFill.cpp:979-980) and the next `Acquire` bumps Gen; every record naming `{slot,gen}` precedes `destroy{slot,gen}` on the ring and every record naming `{slot,gen+1}` follows `create{slot,gen+1}`; the in-order ring plus a `Gen` compare in every server twin table (S7's rule) closes it - no drain wait is needed at delete. `object_death` is already batched; `resource_destroy` becomes `kWaitNone`. The published latch is keyed `{kind,slot,gen}` (PipeMutation.h:294-310). Persistent maps: `Forget()` (PersistentMapTracker.cpp:599-606) drops tracker state only; the pushed bytes were COPIED into SEG_STAGE at `StageOptional` (WireTables.cpp:342) and reclaim waits on `retiredSeq`, so a map released while blocks are in flight is safe; a `glBufferData` respecify after in-flight subdata is ordered by the ring. Client memos holding frontend->handle maps (`MGPipeResourceTracker::Find`, `g_fenceProxies`, the emitters' latches) are GL-thread-only and untouched. Fence: `EmitDeleteSync` frees the Fence slot after emitting (EmitTables.cpp:1507-1519), same ABA answer.

**(6) The two scopes.** After S7 the guard at SlotAllocator.cpp:22-38 loses `:28-29`: `MGPipeSlots()` from the apply thread is unconditionally `Fatal{RoleViolation,"MGPipeSlots"}`. The 36 sites (DirectGLES.cpp 20, Managers.cpp 15, ResourceTracker.h:723) by owner: draw-path (S1 1609, S3 2588/3303/4585, S4 4236/4329/5328/5689, S2 1734/4926/4993, S5 Managers.cpp:2938 `HandleOfBuffer`) - retired by their designs. **Not covered by S1-S5, and each is either a run-ahead op or a waited op:** `DrawArrays`/`MultiDrawArrays` client-side attribute arms (6729/6775, run-ahead ops - refused under split already? ## 5. Monolith / G1

Every change above is `#if MOBILEGL_BUILD_DISAGGREGATED` and behind `RunAheadArmed()`, which is false with no session: `Transport=monolith` never constructs a `ClientSession`, so the emit tables are the monolith adapters and none of `EmitAndWaitTails`, `EmitPresent`, the stamp or the guards runs; `MGPipeValidateForVerb`'s skip is a runtime predicate inside the existing `MOBILEGL_BUILD_DISAGGREGATED` block (:2964-2972 shape) - the pull build's bytes do not move. The one server-side file with a monolith arm, `PipeInputs.cpp`, is compiled only under `MOBILEGL_PIPE_PUSH` and its new `runAhead` argument defaults false. `PipeCalls.def` does not change (no new opcode: the wait class is a generated table, the caps bit is a value).

## 7. Risks and unsettled

- **`resource_subdata`'s texture-half acceptance (D-D5)**: `DrainTextureSubData` clears a level's dirty flag on an accepted reply. Making the row `kWaitNone` requires "accept by construction / decline is Fatal" on the server, or the pmap push keeps a wait per block. Needs S2 + integrator ruling; without it run-ahead only covers draws and the pmap path stays ~6 round trips/frame.
- **`GenerateMipmap`** waits until S2 retires the `GetActiveTextureUnit` read; **`set_storage_block_binding`** and **`resource_copy_region`** (`GetTextureObject(GlName)` sticky, PipeApplier.cpp:742-743) are `kCtxVerb` rows that still read client state - either wait (`kWaitApplied`) or S2/S4 migrate them; list for S8.
- **GPU-write marks are client-side and conservative** (GpuWritePending.cpp:141-147); `OnGpuWritten` events from the server (`MarkBufferGpuWritten`) now arrive late - the client's own marks already cover the draw-time set, so late narrowing is harmless; confirm no server-only producer exists for XFB (`EndStreamOutput` is client-marked, :164-167).
- **EGL RPC vs run-ahead** (§4(3)): the wait-before-forwarder rule adds one full drain per make-current/surface event; acceptable (startup-time), but `ServerSwapEGLBuffers` is NOT on that list (present is the swap).
- **Event-ring capacity** (256 KiB): a writeback slice is a quarter ring (GpuWritePending.cpp:187-200) and the readback row waits, so flow control is the only new requirement; consider `MOBILEGL_IPC_EVENT_KB` if the per-draw `kEventGpuWritten` traffic under SSBO workloads (Iris) trips the full latch every frame.
- **The `VerbBarrier==0` control's meaning** after P5e; and whether `Flush` (kCtxVerb, emitted?) should become the doorbell point of ARCHITECTURE §11.6 - not settled here.
- **Thread placement** (P5D report §"什么没完成" 2) is out of scope by the user's instruction; the measurement plan reports per-thread ms/frame so the comparison survives it.
