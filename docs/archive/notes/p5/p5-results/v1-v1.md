## 1. What landed

**The thread (charter 1).** `ServerLoop::Start` spawns `mgl-srv-apply`; the thread names itself, resolves
`MOBILEGL_IPC_SERVER_AFFINITY` (`auto` = `ShaderCompilePool`'s 85%-of-peak cpufreq rule re-derived as a
MASK, `off` = 0, or a number), applies it with `sched_setaffinity`, and **logs the RESOLVED mask** (0 on this
WSL box: no cpufreq tree, so "do not pin" rather than "pin to a guess"). It parks through
`Doorbell::Wait(control.consumerParked, ready, spinUs, kWaitForever)` and treats `Wait == false && Dead()` as
shutdown. The park predicate is THREE things - ring head moved, stop requested, control request pending -
not `SessionConsumer::WaitForWork`'s one: a `Notify` is consumed by one `Park`, so a predicate that cannot
see the control request re-parks for ever (that is red-check case `park-predicate-loses-control`, which
must TIME OUT). `Stop` = set stop, ring, wait for the exit flag with a **5 s bound**, then `join`; a bound
that expires is `Fatal{ApplyThreadJoinTimeout}` + abort, never detach (a detached apply thread still owns
the context and reads rings the client is about to unmap).

**The EGL migration (charter 2).** `ServerLoop::CreateBackend` builds the server's private
`BackendObject_DirectGLES` (or `_DirectVulkan`) on the app thread and runs its non-GL `Initialize()`; the
context is created and made current LATER, on the apply thread, when the client's `eglMakeCurrent`
crosses as a blocking control request (`RunOnApplyThread`: one-slot mailbox, caller-serialised, runs
INLINE when already on the apply thread - which the teardown path needs, and inline when no thread exists
yet). Twelve free-function forwarders `Server{InitializeEGLDisplay, CreateEGLWindowSurface,
ResizeEGLWindowSurface, CreateEGLPbufferSurface, MakeEGLCurrent, SwapEGLBuffers, SetEGLSwapInterval,
ReleaseEGLSurface, ReleaseEGLResources, InitCapabilities, InitWindowSurface, SetWindowHandle}` are the seam
c1 needs; `ServerMakeEGLCurrent` and `ServerInitCapabilities` also **re-publish the CapsSnapshot** on
success (R-12 arm (a): a second arrival IS the invalidation). The backend is **destroyed on the apply
thread, while it still owns the context**, by the thread itself on its way out - so `~BackendObject_DirectGLES`
→ `DestroyEGLContext` never runs on the app thread. Evidence it works: on the joint build the log shows
`GL_VENDOR: Mesa` / `GL_RENDERER: llvmpipe` written by thread `mgl-srv-apply`, `CapsMirror generation 2
adopted` on the client after make-current, and `destroying the server's BackendObject on mgl-srv-apply,
which is the context owner` at teardown (`~/w7/p5-v1-joint-preflight.log`).

**The hook (charter 3).** `MG_Backend::Init()` gains one `#if MOBILEGL_BUILD_DISAGGREGATED` block before the
`switch`: if `Transport != Monolith` → `InitSplitRoles()` = server backend → the two CallMask halves (§1
"caps") → `ClientSession::Start` (s1/c1's; it does the handshake and ends by calling `ServerLoop::Start`) →
the client's backend object into `pActiveBackendObject` → `InitSpecificBackendLibs()` (which fills
`gBackendFunctionsTable` from THAT object, i.e. c1's emit table) → `LogBackendInfo()`. c1-v1 §8.2's order,
exactly. A failed bring-up leaves `pActiveBackendObject` null and returns - **no fallback to the switch**.
The counterpart `ShutdownSplitRoles()` runs first in `DestroyImpl` (§1 "teardown").

**The applier (charter 4, 5).** `PipeApplier::Attach` builds w1's decoder ON the apply thread (its
constructor installs the process-wide apply hook) and points it at `ServerVerbSink`. `ApplyOne` =
`StampVerbBoundary(op)` → `DecodeAndApply` → `LeaveApplier()`; s1's `SessionConsumer::ApplyOne` advances
`appliedSeq` by exactly one after it returns, and nothing here touches `RingControl`. No batching. After each
drain batch: the decoder tally and the session watermark must agree (`Fatal{ProtocolCorruption,
"appliedSeq batched"}` otherwise) and `RetireThrough(AppliedSeq())` runs once. p1's rule verbatim:
`MGPipeVerbForWireOp(op)`, `kVerbCount` ⇒ nothing, else `MGPipeServerStampVerbBoundary(verb)` once before the
applier; `MGPipeServerClearVerbBoundary()` on leaving - **inside `ApplyOne`, before the watermark publishes**
(§6). `PipeApplier::m_residualPulls` is deleted; `ResidualPullCount()` forwards to `MGPipeResidualPullCount()`.
`ServerVerbSink` is the consumer for the five class-B verbs that have no `MGPipeApply*` entry point: `Clear`
(five kinds, three value classes, against the BOUND framebuffer - `MGPClear::Fbo` is null by c1's ruling),
`Blit`, `Present` (through the server's own `Present`, so `present ↔ eglSwapBuffers` stays 1:1;
`FrameSerial == 0` = stamp your own), `ReadPixels` (writes exactly `DstSize` bytes into the reply slot,
`DECLINED` when no table, `ERROR` on zero size - never a silent non-answer, because the client is parked on
that seq), `DrawVbo` (single non-instanced arrays / indexed draw; `NumDraws != 1`, instancing and any user-index
span are DECLINED BY NAME - P8's). Per-verb tallies exist for lanes to assert against.

**R-11 (charter 6).** `StagedShadowStore` (header-only, keyed by the resource twin's address) copies
`[offset, offset+size)` into server-owned storage and records the EXACT covered ranges (adjacent runs merge,
gapped ones do not). `Ops_H_SubData` / `Ops_H_FlushRange` / the respecify base go through
`MGL_SERVER_STAGED_ADOPT`, whose non-split expansion is the ORIGINAL expression character for character
(`raw - offset`), so push/verify compile what they compiled before. Drops at destroy, at a successful
`map_persistent`, and at context death. The integrator's M-6 ruling is enforced as
`Fatal{StageSnapshotTooNarrow, "<site>"}`: `UploadRangeFrom` and the tier-1 invalidating map in
`Ops_H_FlushRange` check their own range, and the three-tier drain's queue is checked at its two
server-shadow call sites (`Ops_H_Readback`, the handle-arm ensure path) by
`RequireStagedCoverageForPendingRanges` **before** `FlushPendingRangesFrom` is called - the pinned body is
untouched (§5). The store's copying arm is a constructor parameter, not a `MG_Config::Transport` read, so
`StagedShadowTest` builds one of each and asserts the DIFFERENCE.

**Caps defaults (charter 7).** `InitSplitRoles` sets both halves before `Accept`: `SetCapabilityBits(0)`
(explicit: `kCapNeedsHostIndexBytes`/`kCapNeedsHostUboBytes` are 0 for all of P5 by table 0) and
`SetConsumedSubsystems(ConsumedSubsystemsFor(type))` = `kMGPipeSubsystemsMigratedAtP4a` for DirectGLES,
the same minus `kMGPipeSubsystemResources` for DirectVulkan (which registers no resource ops) - stated from
what the backend IS, **not** derived from the process-wide `MGPipeGetResourceOps()`, which under inproc
answers with whatever the client half registered. `AssertConsumerMaskIsHonest` runs after `Initialize()` and
is `Fatal{ConsumerMaskLie}` if the mask claims the resource family while no op table is registered (ID-39's
shape, one level down). On the joint run the client adopted `callMask=0x1fff00000000`.

**Teardown (charter 8).** `ShutdownSplitRoles()` → `ClientSession::Stop()`, which IS table 3's order:
publish + bounded drain → `transport->Shutdown()` (= `Doorbell::Kill`, the only thing that wakes a
`kWaitForever` park) → `ServerLoop::Stop()` (bounded join; the thread applies whatever is still queued,
detaches the decoder, destroys the backend on itself) → only then the emitter-owned things → transport
closed. It runs at the TOP of `DestroyImpl`, so the apply thread is joined before `PipeStats::Shutdown()`
dumps and before `pActiveBackendObject.reset()`. **The sync/query registries keep today's order** (drained at
`MobileGL/Init.cpp:62/:67`, before `:68`); CONTRACT §4's known open item is recorded as "P5 keeps today's
order" in `BackendObjects.h`, and it is P10's to move. Under `GLIBC_TUNABLES=glibc.malloc.tcache_count=0`
(exported by the gate) every case, the shutdown case included, is green; `StopKillsTheDoorbellJoinsAndTheThreadReallyExits`
asserts the thread really PARKED first and that `Stop` returned inside the bound.

## 6. The ordering defect - what it was, and its fix

My last words before the outage were "Found a real ordering defect via the red-check baseline". Re-derived
today by re-running that baseline under load (`ctest -R 'ServerLoopTest|StagedShadowTest' -j 8 --repeat
until-fail:40`): **red at run < 40** - `TheSessionWatermarkAndTheDecoderTallyAgreeAfterEveryRecord:398`
(`DrainedRecords()` 7, expected 8) and `AClearRecordCrossesAndIsStampedAsAVerbBoundary:365` (0, expected 1).

**The family is "server-side bookkeeping ordered AFTER the watermark that releases the client".** s1's
`SessionConsumer::ApplyOne` publishes `appliedSeq` the instant the apply callback returns, and publishing
`appliedSeq` is what makes the client runnable (R-1). Anything the apply thread records about a record AFTER
that publish is visible to the client only eventually. Two members:

- **(a) `LeaveApplier()` after the drain batch** - the stamp-clear ran while the client was already touching
  `gPipeInputs`: a second writer, table 3's one forbidden thing. **Already fixed in the WIP** the integrator
  preserved: the clear is inside `ApplyOne`, before the publish (`PipeApplier.cpp`'s block says so, and
  `~/w7/p5-v1-patch3.py`'s timestamp shows the red-check anchor moved from `ServerLoop.cpp` to
  `PipeApplier.cpp` at 16:32 on Sep 11 - that was the fix in flight).
- **(b) `m_drained` tallied once per batch, after the publish** - unfixed in the WIP, reproduced today,
  **fixed in `23c04687`**: the tally moves inside the apply callback, before s1 publishes, so
  `DrainedRecords()` can never lag `appliedSeq`. 200 consecutive `-j 8` runs of the two cases green after the
  fix; the gate's 100× flake sweep is green; red-check `drained-tally-removed` is the deterministic control.
  (A third, `retiredSeq`, is NOT a defect: R-9 lets every watermark but `appliedSeq` publish late, and the
  case polls it with a 2 s bound instead of reading it once - the bound is what keeps it a check.)

Which of the two the sentence referred to I cannot know from the record; both were in the red-check
baseline's failure mode, (a) was fixed in the tree I inherited and (b) was not. Both are fixed now, and the
gate now sweeps for this family under load.
