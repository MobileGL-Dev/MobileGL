## 3. R-17's real size versus the estimate

R-17 costed it as "~41 direct call sites converted to the `MGP_*` thunks, the two install functions, and 37 thin client
emitters over `EmitAndWait`". **The call-site number was exactly right (40, measured). The emitters really are thin. The
ROUTING was not, and it is bigger by four rows and one whole mechanism.**

The generated table signature is the **P2-era monolith interface**: `void (*Name)(const Payload*, ...)`,
async-with-handle, no return value, no companion pointer. Of the 37 apply entry points, as the tables stood
(`~/w7/p5-c1-r2-sigdiff.py`, which prints the pairing):

| | count |
|---|---|
| the row could carry every argument the call site passes today | **24** |
| it could not | **13** (14 counting `SetResidualValueState`'s type mismatch) |

The thirteen split three ways, and only the first is a generator question:

**(a) Nine carry a blob companion** — `chunkBytes`, `blobBytes`, `parameters`, `bytes` — which is CONTRACT §2 table 1's
"companion pointer today" column. This is the whole generator change and it is **five lines** in `Call.Signature`: a
`kHasBlob` row gains `const void* blobBytes, Uint64 blobByteCount`, *exactly* as a `kVarTail` row already gains its pair.
Ten rows gained it (the nine plus `GetCaps`, which has no applier). `--check` up to date, `--self-test` 9/9 trips,
`gen_pipe_field_ownership --check` up to date. No `.def` file was touched.

**(b) Four return a value the row cannot** — `ResourceCreate`, `ResourceRespecify`, `ResourceSubData`,
`SetTextureParams` return `Bool`, `MapPersistent` returns `void*`. These are exactly CONTRACT §2's reply-slot rows.
`MGPReplySlot` is `{Uint64 Id;}` — an **identifier, not a value** — so a *reader* had to exist before minting one meant
anything. That is the reply mailbox (§4), and it is the part of R-17 that no amount of "thin emitter" covers.

**(c) Four cannot go through a generated row at all**, each for a written-down ruling. They are a hand-written third
table, `gMGPipeRouteEscapes`, installed and uninstalled by the same two functions so there is one mechanism and not two:

| row | why | what would overturn it |
|---|---|---|
| `ResourceRespecify` | `initialBytes` has no `kHasBlob` and R-13.3 forbids giving it one | give `MGPResourceDesc` a blobref (c0's `MGPipeTypes.h`) |
| `ResourceFlushRange` | R-13.2: a blobref here "would be a second, forgeable way to say the same thing" | the same |
| `MapPersistent` | `size` + `seedBytes` have no carrier (`MGPHandleOnly` is `{Handle, Kind}`) and it returns `void*` | give `MGPHandleOnly` a size, and P6 a real remote map |
| `CreateShaderState` | **seven** blobrefs (`Spirv[6]` + `Reflection`) and two typed frontend pointers; one `blobBytes` pair cannot express seven runs, and serialising under monolith to deserialise in the adapter would put `EncodeProgramArtifacts` on the monolith path, which `PipeApply.h` explicitly promises it is not | measure that a per-stage SPIR-V run beats one archive |

So: **33 rows through the two generated tables, 4 through the escapes, 37 total** — and `PipeCatalogueTest` asserts both
numbers, because a row moved out of the generated tables with its escape forgotten would otherwise read only as a
smaller count while its call site took a null.

**Three of the 37 wrappers take one argument more than their applier**, and the extra is always a byte count the record
does not declare (CONTRACT §2 rule A requires it under split; five rows already declare and the wrapper reads it back):
`SetGlobalConstants` (the length is `GetUBOSize()`), `ResourceSubData`'s **texture half** (`levelBytes` — this closes
row 7's open half, "the byte count is the server's to compute", which table 1 itself says "cannot be a bounds check"),
and `BufferSubDataResident`. A defaulted argument was rejected: a default lets a site that *has* the number forget it and
still compile, and the failure is a silently short upload.

## 4. Every ruling made this round, with evidence and what would overturn it

**R-17.1 — the reply mailbox is one entry deep, thread-local, and has no default answer.**
Evidence: `ReplySlot.h` — "under R-1's verb barrier the in-flight depth is one". A second posting before the first is
taken is not a capacity problem, it is a barrier that has stopped holding, so it is `Fatal{ReplyOverrun}`. A take with
nothing posted is `Fatal{ReplyMissing, "<row>"}` — **not `false` and emphatically not `true`**: "always accept" is
ID-39's 66 lost uploads and "always refuse" is an emitter that re-sends for ever. `ERROR` is refused as an acceptance
answer at all (a transport fault is not a resource decision). Overturned when R-1's barrier retires for a family: the
mailbox becomes a slot pool keyed on seq, which is what `Transport::ReplySlot` already is on the wire side.

**R-17.2 — the install is driven by an `inline` variable in the header, not a static initialiser in the .cpp.**
This one was **found by the gate, not designed**. The first version put the installer in `PipeRoute.cpp`'s dynamic
init, on correct reasoning about constant-initialised inline variables — and five `CsoCacheTest` cases SEGFAULTed in the
push and verify lanes, because every `MG_Test` target is its own binary over a static archive, `CsoCache.h` reaches the
table through an inline thunk and names no symbol in `PipeRoute.o`, so the linker dropped the object. The shared library
linked it and was fine, which is the shape that ships. An inline variable fixes both halves: its initialiser is a COMDAT
in every TU that includes the header, and naming `MGPipeInstallMonolithTables` from that header forces the archive
member into the link. Overturned by a toolchain that defers inline-variable dynamic init past first use.

**R-17.3 — the client emitters run the MONOLITH adapter when they find themselves on the server role's thread.**
The second gate-found defect, and the more serious one. `gMGPipeScreen`/`gMGPipeContext` are **process** globals; under
`inproc` the server role is a thread in the same process, so the apply thread running the server's own backend (the EGL
bring-up, `InitCapabilities`, the applier) reaches these very emitters. The first joint run died
`Fatal{BarrierTimeout, "ResourceRespecify"}` logged by **`mgl-srv-apply`**, thirty seconds in: the apply thread had
published a record and was waiting for itself to apply it. The predicate is v1's `ServerLoop::OnApplyThread()`; the
answer is not "suppress the record" but "run the server's own code", which is what `PipeWireCodec` already does on the
decode side. Under `spawn` it is constantly false in one process and constantly true in the other, so it costs one
atomic load. **This is also what makes the integrator's `ScopedApplierEntry` bracket safe to add** — on the apply thread
the emitters never reach `EmitAndWait` at all.

**R-13.2 / R-13.3 — the contract's prescribed follow-ups had no producer, and now do.**
CONTRACT §2 row 19 says initial content "arrives as `ResourceSubData` records immediately after this one" and row 20
says the flush's bytes "arrive ahead of it". Nothing emitted either. Evidence: the joint run died
`Fatal{UncarriedInitialBytes, "resource_respecify"}` on the first `glBufferData` with data, and then
`Fatal{ProtocolCorruption} resource_flush_range ... a non-empty flush carries no bytes (offset=0, size=120,
storage=120 bytes)`. Both are now emitted through `MGPipeForEachSubDataRecordRange` — the contract's own route ("reuses a
path that is already chunked and already acceptance-gated") — **split-only**, because under monolith the applier reads
`initialBytes` directly and a second upload would be a real change in the control arm. The flush stages **exactly** its
own range, never the whole buffer, because widening is what ID-37 forbids. Overturned if a caller is found that needs
the bytes and the range in one record — which cannot happen while the barrier holds.

**ID-49 — `DstSize` is the tight extent and the client scatters.** Ratified as issued and implemented; the emitter keeps
a zero-copy fast path when the pack state is neutral, and `TheFastPathIsTakenExactlyWhenTheScatterWouldChangeNothing`
drives the predicate and the scatter together, because testing either alone would pass a predicate that said "tight" for
a layout the scatter would have rearranged. The rule is format-agnostic, so the depth/stencil reads the 21 split entries
touch take it with no special case.

**Ratified from round 1, no further debate, and unchanged:** `MGPClear::Kind` (`kRemoteClearWhole` only); the `Fbo` and
`ReadFbo`/`DrawFbo` nulls; `OnReadPixels` writes exactly `DstSize` bytes — which ID-49 now defines as the tight extent,
so "exactly `DstSize`" means "into the reply", and the application's layout is the client's business.

**R-12 — which of the four reverse-channel arms are wired.** Asked and answered: **`OnGpuWritten`, `OnBufferWriteback`
and `OnSurfaceChanged` are wired; `OnCapsInvalidated` is not, and deliberately.** DirectGLES has no
`OnCapsInvalidated` producer at all; c0's ruling is that a **second CapsSnapshot arrival IS the invalidation**, and v1's
`ServerMakeEGLCurrent`/`ServerInitCapabilities` republish one. The joint log shows it working:
`CapsMirror generation 2 adopted`, then `generation 3`. So the fourth arm has a *consumer* and no *producer*, on
purpose, and adding one would be an eleventh `MGPipeCallbacks` slot for something already expressible.

## 9. The G1 codegen trap (round 1) — self-contained, for ARCHITECTURE/MEASUREMENTS

> **A Bool-valued macro is not a drop-in replacement for a pointer-valued condition, and the difference is 144 bytes of
> `.text`.** CONTRACT-P5 §7 requires the 41 call sites that null-check a `GLFunctionsTable` slot to stop doing so under
> split, because with no null slot in the client's table every one of those checks answers "supported" and the fallback
> behind it silently disappears. The obvious conversion is a macro that answers the capability question as a `Bool`:
> `if (MGL_BACKEND_SLOT_CAP(Slot, kCapX))`. In a *pull* build that macro expands to exactly the null check it replaced,
> so it looks free. It is not. Two sites in `GL_Getter.cpp` were written as `if (const auto f = TABLE.GL.Slot)` — a
> condition **with an init-statement** — and rewriting them as `if (BOOL_MACRO) { const auto f = TABLE.GL.Slot; ... }`
> is semantically identical and generates different code: G1 came back `.text -144` with **2 symbols resized**,
> `GLImpl::GetInteger64v` −150 and `GLImpl::GetIntegerv` +2. The fix is a second spelling,
> `MGL_BACKEND_SLOT_PTR_CAP` / `_PTR_LOCAL`, which in a pull build expands to **the slot expression itself**, so the
> init-statement survives verbatim and the codegen is byte-identical. `GL_Sync.cpp`'s `FenceSync` had the same shape and
> did *not* happen to move; it was converted to the pointer form anyway, because "did not happen to" is not a property.
> **The general rule: when a gate requires byte-identical codegen, a macro must preserve the EXPRESSION SHAPE of what it
> replaces, not merely its truth value.** A rewrite that changes an init-statement into a block, a short-circuit into a
> call, or a pointer into a `bool` is a codegen change even when it is not a behaviour change.
