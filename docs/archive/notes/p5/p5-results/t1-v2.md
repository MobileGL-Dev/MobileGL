## 3. Two things the integrator's brief got wrong, both load-bearing

### 3.1 `Fatal{BarrierViolation, "DrawVbo"}` does not exist

The round-2 brief says `~/w7/p5-v1-joint-isplit-barrier0.log` recorded *"eighteen
`Fatal{BarrierViolation, "DrawVbo"}`"*. It did not:

- `grep -c Fatal ~/w7/p5-v1-joint-isplit-barrier0.log` → **0**.
- `grep -rn BarrierViolation` over the whole tree → **0**. There is no such Fatal kind anywhere.

The 18 entries in that log are `Subprocess aborted` with **no output after `[ RUN ]`**. This is
ID-50's caveat made concrete: ctest captures only gtest output, the library's console sink is
compiled out of this configuration, and the three `DirectGLES.Split.` lanes set no
`MOBILEGL_LOG_FILE_PATH` (only the `PersistentMapArm` lane has one,
`MG_IntegrationTest/CMakeLists.txt:1945`). **No `MGLOG_` output of any level reaches CI from the E1
selection.** So the barrier knob has no named diagnostic a control can require. Recorded as a debt in
§5, not papered over.

### 3.2 The `:290/:295` assertion came from an entry the E1 filter excluded

`ClearThenReadPixelsScenario.cpp:290/:295` ("reading back 0 where >200 was cleared") is real and is
in that log — but it belongs to
`DirectGLES.Split.**SmallRing**.ClearThenReadPixelsScenario.AMultisampleResolveBlit…`, and the old E1
filter was `DirectGLES\.Split\.(Triangle|ClearThenReadPixels)`, which the intervening `SmallRing.`
excludes. Every entry the old filter *did* select aborted silently. **A control whose selection
contains no case able to say why it failed cannot assert its own failure reason at all.**

So E1's filter is now `DirectGLES\.Split\.(SmallRing\.)?(Triangle|ClearThenReadPixels)` and E3(a)'s
is `DirectGLES\.Split\.(SmallRing\.)?PersistentCoherentMapScenario`. The SmallRing entries are the
same scenarios under the same transport with `SEG_CMD`/`SEG_STAGE` at their floor, so this widens the
selection strictly within E1's charter (BRIEF §7 E3(e) is the same lane). **This is the one change
that wants a ruling** — see §5.

### 3.3 Why I did NOT use ConfigLoader's per-knob line as the evidence

`ConfigLoader.cpp:385-393` logs `MOBILEGL_IPC_VERB_BARRIER=0 is the R-1 NEGATIVE CONTROL …` and
`MOBILEGL_IPC_PERSISTENT_BLOCK_KB=0 is the E3(a) NEGATIVE CONTROL …`. It is the obvious thing to grep
for and it is **not evidence**: it is written at config load by every process in the run, whatever
happens afterwards. A setup abort carries it too. It proves the knob was *read*, never that the knob
caused the red. Stated here so nobody "completes" this work by reaching for it. (It is also
unreachable — §3.1.)

For E3(a) the knob DOES have reachable evidence: with the push off, the write that no GL call
announces cannot reach its draw, and the cases fail on their own wording
(`PersistentCoherentMapScenario.cpp:414-417`, `:442-443`, and the counting case's `cannot have
pushed … zero bytes` at `:531-541`). That is what the E3(a) control requires.
