## 2. Finding 5 — the pad-bit case never sent the bit

`RingProducer::Reserve` masks `kRecPad` out (`flags & ~kRecPad`), so `Reserve(7, kRecPad, 16)` put `flags=0`
on the wire and the case was green with Pop's kind check deleted. The case now does what a codec with its
own header struct does: `Reserve(7, kRecNone, 16)`, then stamps `kRecPad` into the eight header bytes
directly. `ApplyOne` must deliver it (`seen==1`, kind 7, the bit intact, `appliedSeq==1`), and the opposite
control follows in the same case: a header wearing `kRecPad` whose kind IS `kRingPadRecordKind` is a
genuine filler, still vanishes, and does NOT advance `appliedSeq` (R-9). That last assertion is what this
case adds over ID-43's `RingTest.TheTwoFlagSpacesAreDisjointByTranslation`, which is the same control at
the ring; this one is at the session.

**Red once by** deleting `&& header.kind == kRingPadRecordKind` from `RingConsumer::Pop`:
`SessionTest.ARecordWearingThePadBitIsDeliveredRatherThanEatenAsAFiller ... ***Failed` on its own
message ("the record was skipped as a wrap filler because it wore bit 2 …"). Chosen over deleting the case
because the session-level half (appliedSeq counts the record, not the filler) is not stated anywhere else.

**§8.2 of s1-v1.md is re-pointed here**: the kind-check control is this case AND

## 6. GitHub run 35079459114 — `TheMemoryLedgerIsPerRoleAndIsReleasedOnClose` red on CI (add-on)

**Diagnosis: CONFIRMED, with the mechanism one step sharper than proposed.** The kernel stores
`mm->hiwater_rss` only when RSS is about to DROP; `task_mem()` reports `VmHWM = max(stored, rss-at-this-read)`.
Within ONE read of `/proc/self/status` the pair is therefore self-consistent — but the wave-1 sampler read
the two keys in TWO passes (one `fopen` per key), and the second `fopen` itself grows RSS (stdio buffer,
allocator), so the second pass's `VmRSS` can exceed the first pass's `VmHWM`. Probe (`~/w7/p5-s1-probe/`,
kernel 6.18.33.2-microsoft-standard-WSL2):

```
pass1: VmHWM=3660 VmRSS=3788 | after touching 4 MiB: VmRSS=7884 > pass1 VmHWM? YES | VmHWM re-read=7884
single-pass reads with 64 KiB growth between them: 0/1000 had VmRSS > VmHWM
```

— two passes disagree by 128 KiB with nothing allocated between them (exactly the CI shape: 4,784,128 <
4,849,664 is 64 KiB); one pass never disagrees. Why CI and not local: only timing — the second `fopen`'s
first-touch pages are more often already resident locally; the race is real everywhere.

**What changed (as ruled).** `ProcessRssBytes(&peak, &current)` reads BOTH keys in one pass (the two old
accessors remain, implemented over it). `SampleRoleMemoryInto(runningPeak, role, kernelPeak, kernelCurrent)`
folds `max(kernelPeak, kernelCurrent)` into a caller-owned running peak (CAS loop — the GL and apply
threads both log memory at phase boundaries) and reports THAT as `PeakRssBytes`, so `Peak >= Current`
holds by construction and never decreases; `SampleRoleMemory(role)` = one pass + the fold into a
process-wide running peak. `RoleMemory.h` documents the rule and the run id. The `LogRoleMemory` line is
unchanged in shape (t1's grep tag `MG_Remote memory[` is untouched).

**Controls.** The CI assertion `EXPECT_GE(sample.PeakRssBytes, sample.CurrentRssBytes)` stays, now true by
construction. New `SessionTest.TheLedgersPeakIsItsOwnRunningMaxAndNeverTheKernelsHighWaterMarkVerbatim`:
a running peak of its own, fed (peak 100, current 200) → `PeakRssBytes == 200`; then (150, 120) → stays
200; then (300, 100) → 300 (the kernel's peak still counts when larger); and one real
`ProcessRssBytes` pass on Linux is non-zero and self-consistent. **Red once by** reverting the fold to
`sample.PeakRssBytes = kernelPeakRssBytes;` → `***Failed` ("the kernel's peak was reported verbatim
although its current exceeded it", 100 vs 200) — the CI line, deterministically.
