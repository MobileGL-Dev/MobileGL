# p5c-audit-v1 — where the `inproc` split still reads the other role's memory

Read-only static audit of `feat/disaggregated` @ `a79a0af69de8c6c53ef985dd23be7eab8cd17641`
(`git rev-parse HEAD`, 2026-09-17). No builds, no tests, no git mutation, no adb. Every
`file:line` below was re-resolved on this head (the contracts' line numbers are from older
heads and drifted; §5 lists the drift found while auditing).

Direction legend: **S→C read** = server/apply-thread reads client memory · **S→C write** ·
**C→S read** · **C→S write** · **shared** = process global both roles touch.

Frequency shorthand: *draw* = per draw/dispatch, *upload* = per upload/respecify, *verb* =
per emitted record, *rare* = per EGL call / make-current / bring-up, *once*.

Phases: P5c = worth fixing now, inproc, before P6 · P6 = spawn transport must replace it ·
P7/P8/P9/P10 = the phase the field tables / ROADMAP already assign.

## 4. Surprises / disagreements with the contracts and ARCHITECTURE.md §17

1. **The texture texel path is the real rule-C violation, and no table names it.** CONTRACT-P5 §0 calls `hostBytes` "the tree's exactly one violation" — fixed on this head. But texture uploads stage the level into SEG_STAGE and `ApplyTextureUpload` then **drops the pointer** ("DISPATCHES TO NOBODY", `PipeApply.cpp:989-1008`); Espryt re-reads the texels from the client `MipmapStorage` (`Managers.cpp:7315`). Every texture-object method the server calls on a client object has **no row in `FieldOwnership.def`**, so the whole family is invisible to `rsp` and to `MOBILEGL_IPC_STRICT_ERRORS`, and `MOBILEGL_IPC_AUDIT=1`'s `0xDD` fill cannot observe it (textures never adopt staged bytes). `rsp` is a lower bound by a wide margin — exactly as `r2-v1.md:79` warned, but the unnamed set is larger than "sticky/non-verb forwards": it is the texture hot path.
2. **SEG_EVENT is fully plumbed and silent.** Segments created, mapped, announced in Welcome, consumer drained after every reply verb (`ClientSession.cpp:836`) — and zero producers repo-wide. Worse: the one live writeback producer bypasses the ring with a raw host pointer (`Managers.cpp:2339-2343`), and the installed consumer would **reject** the ring's own blobref convention (`ResourceTracker.h:560-564` rejects any real `Seg`). A producer added tomorrow would be dropped, not delivered.
3. **8 of 10 `MGPipeCallbacks` are never installed** — only `OnBufferWriteback`/`OnGpuWritten` have assignment sites (`ResourceTracker.h:606-613`), and both are invoked **in-line on the apply thread** straight into client `MG_State`. `OnGlError`, `OnSurfaceChanged`, `OnCapsInvalidated`, `OnMipLevelsGenerated`, `OnXfbScatterReady`, `OnTexturePullRequest`, `OnTextureWriteback`, `OnLog` are declaration-only.
4. **`MGPDrawInfo::XfbCpuCapturedVertices` / `kDrawHasXfbCount` ride nothing.** CONTRACT-P5B:163-164 says the field "rides when the client's XFB accounting has a value"; on this head it is written 0 (`EmitTables.cpp:402`, `:1873`) and read by nobody.
5. **The barrier's client-half assertion is half-implemented.** CONTRACT-P5 §4 says "the client checks [`InBarrierWait`] when it touches `gPipeInputs` outside a barrier" — the function has zero call sites (`ClientSession.cpp:880`). Only `ApplyThreadIsInsideApplier` is enforced, and only at emit (`ClientSession.cpp:748`). The two client writes that run outside the barrier (`PipeFill.cpp:2798` into `gPipeInputs`, `:2656` into `g_applier`) are covered by the barrier's post-condition, not by the advertised check.
6. **`GetCaps`'s two blobrefs are answered by the snapshot, not the record.** The `GetCaps` wire record is dead (decoder declines, no emitter); ARCHITECTURE §17's "GetCaps 两个 blobref 的载体" open item is in practice the `CapsSnapshot` frame, which is wire-clean. The open item is record hygiene, not a missing carrier.
7. **Magma was left out of three fixes Espryt got.** `pActiveBackendObject` routing (#37 vs `Utils.cpp`), mip-level re-derivation (#14 vs `DirectGLES.cpp:8080-8111`), and the `MarkGpuWritten` callback (#30) all have a DirectGLES arm and an untouched DirectVulkan twin. CURRENT_STAGE_PROGRESS §5's "Magma split compute/image: 82 of 89 wrong answers" is consistent with this.
8. **Windows inproc does not exercise the POSIX attach path.** `AttachInProcess` aliases the server's `ShmSegment` objects on `_WIN32` (`ShmSegment.cpp:352-359`); the dup+`Adopt`+`Map` arm that P6 generalises is POSIX-only. Windows-lane green says nothing about segment lifetime discipline.
9. **Stale doc/code citations found while auditing** (all content still true, only the numbers drifted): `StagedShadow.h:11-14` and `PipeApplier.h:33-37` repeat CONTRACT-P5's `Managers.cpp:1980-1983/:2035/:2000/...` (now `:2165`,`:2225`,`:2183`,`:2271`,`:2279`,`:2315`,`:3179`,`:5393-5396`); `PipeWireCodec.cpp:1872` cites `PipeApply.cpp:702` for the subdata length check (now `:715`); CONTRACT-P5 table 3: `PipeInputs.h:706`→`:806`, `PipeApply.cpp:396/402`→`:409/:415`, `Managers.cpp:5490-5496`→`:5806-5812`, `Init.cpp:44`→`:63`, `Managers.cpp:2594`→`:2769`; `EmitTables.cpp:21-22` header comment says B=11/C=58 while its own `static_assert`s pin B=54/C=15 (`:1643-1667`).
10. **`EmitBlitNamedFramebuffer` already carries the two FBO handles** (`EmitTables.cpp:776-777`) — the "scoped client binding" inproc dependency #1 is therefore removable inproc (P5c), not only at P6: the sink can resolve `ReadFbo`/`DrawFbo` server-side today. Same for the mip registry lookup (#4, `MGPMipPlan::Res` already crosses).
