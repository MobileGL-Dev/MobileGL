## 3. The finding I would most like the other packages to read

**`MGPWireRecHeader::Flags` and `Transport::RingRecordHeader::flags` are the same 16-bit
field, and the two flag spaces collide.**

- `MG_Pipe::kVarTail` is `1<<2`. `Transport::kRecPad` is `1<<2`.
- `MG_Pipe::kHostSpan` is `1<<3`. `Transport::kRecBorrowSlot` is `1<<3`.
- `MG_Pipe::kReplySlot` is `1<<4`. `Transport::kRecVarTail` is `1<<4`. **(Found by the
  reviewer, not by me — §10.)** Five of the six call-flag bits alias a ring bit; only
  `kOptional` is free, and only because `RingRecordFlags` has not reached `1<<5`.

`PipeWire.inc:37` documents the field as *"MGPipeCallFlags of the call, for asserts and
tracing"*, which invites an encoder to stamp `MGPipeCallFlagsFor(op)` straight into it. Doing
that makes `RingConsumer::Pop` **skip every one of the nine `kVarTail` records as a wrap
filler** — silently, with no checksum anywhere on this ring — and makes both `kHostSpan` rows
look like slots borrowed into the GPU timeline, so they would retire on
`completedFrameSerial` instead of on apply.

**The encoder translates**: `kNeedsAck -> kRecNeedsAck`, `kHasBlob -> kRecHasBlob`,
`kVarTail -> kRecVarTail`; `kReplySlot`, `kOptional` and `kHostSpan` have no ring bit and get
none. The call's own flags are read from the **opcode**, through `MGPipeCallFlagsFor` — which
is what c0 generated that table for. The `static_assert`s in `PipeWireCodec.cpp` now pin
**both enums exhaustively** — each full mask, the exact overlap, every colliding pair by name,
and the completeness of the translation — and
`PipeWireCodecTest.AVarTailRecordIsNotSkippedAsAWrapFiller` is the trip wire.

**Ask for c0:** `PipeWire.inc`'s comment on `MGPWireRecHeader::Flags` should say *ring framing
flags* rather than *MGPipeCallFlags of the call*. It is a one-line generator edit and it is the
comment that would have caused the bug.

## 4. Rulings I made, each with what would overturn it

**W-1 — `CreateShaderState` crosses as ONE blob, not seven.** `EncodeProgramArtifacts` already
serialises `SpirvArtifacts::generatedSpirv`, i.e. every stage module, so `Reflection` names the
whole archive and `Spirv[0..5]` stay all-zero ("absent"). A declared `Spirv[i]` is
`Fatal{ProtocolCorruption}` rather than ignored, for `resource_flush_range`'s reason (contract
§6.3): a second, forgeable way to say the same thing is worse than no way at all. Evidence that
this costs nothing: `PipeApply.cpp` reads **neither** `desc.Spirv[]` nor `desc.Reflection` —
`MGPipeApplyCreateShaderState` takes `(desc, link*, spirv*)` and reads the modules out of
`spirv->generatedSpirv`. Shipping them twice would double the largest record in the catalogue
for a reader that does not exist.
*Overturn:* a measurement showing per-stage runs beat one archive — and then the archive has to
stop carrying `generatedSpirv` **in the same change**, or the two disagree.

**W-2 — every var-tail starts 8-byte aligned inside the record; the encoder zero-fills the
gap.** Eight of the nine `kVarTail` rows are already aligned by construction. `DrawVbo` is not:
`MGPDrawRange` is **twelve** bytes, so an odd `NumDraws` leaves the conditional `MGHostSpan`
(a pointer and two `Uint64`s) on a 4-byte boundary. P5 emits no host span at all, so the rule
costs nothing now; it is stated now because the phase that arms `kDrawHasUserIndices` would
otherwise discover it as a misaligned load on a device. Pinned by
`DrawVboConditionalSpanTailIsEightAlignedAndSurvives`.
*Overturn:* nothing — it is free. (Contract table 1 row 16 already rules that the span **stays
in the tail** in P5, which this implements unchanged.)

**W-3 — `SEG_STAGE` is reclaimed by the ENCODER, behind `retiredSeq`, from marks it holds
itself.** `SEG_STAGE` is client-owned memory (table 1: *"client stages, server copies"*) and the
server only reads it, so the client is both producer and reclaimer; what it may not do is free
ahead of `retiredSeq`, which is R-11's whole content on this side. The record carries no field
saying where its staged bytes end, so the encoder remembers `{seq, stage cursor}` per record
and releases up to the newest mark the server has retired. **This does not depend on the verb
barrier**, so it keeps working when R-1's barrier retires family by family.
*Overturn:* a phase that lets the server borrow a staged run into the GPU timeline — then the
mark has to move to `completedFrameSerial` and the two stage tails stop being published
together.

**W-4 — the `0xDD` audit fill is the DECODER's, and it is exact.** R-2.5 says "the server fills
a retired record's SEG_STAGE bytes"; the thing that knows which bytes those are is the decoder,
which resolved them. It records up to eight runs per record (`CreateShaderState`'s seven blob
members plus a tail) and memsets exactly those after the applier **returns**, leaving the stage
ring's own record headers intact. `PoisonedStageBytes()` is the counter a t1 lane asserts is
non-zero with the knob on — an instrumentation that cannot be observed to have run is
decoration.

**W-5 — `CheckBlobIsHonest` could not carry R-2 arm 2, so arm 2 is its own function.** Whether
a record *carries content* is a property of its OTHER fields (`ChunkMask`, the destination
range, the stage mask), which `(op, blob)` does not see. So `CheckBlobIsHonest` implements arms
3 and 4, `RequireDeclaredBlob` is arm 2, and the decoder's per-op arm calls the second one
exactly where the payload says content is implied.
**And it needed a third shape the brief does not name.** A blobref is honest when it is either
fully declared or **all three fields zero**. `Seg` or `Offset` non-zero with `Size == 0` is
neither — and it is precisely what a MONOLITH emitter writes today (`Seg = None`,
`Offset = (Uint64)&link`, `Size = 0`, e.g. `ProgramEmit.h:180-195`). Reading that as "absent"
would **silently drop the bytes of every record an unconverted emitter sent**, so it is Fatal.
Pinned by `AHalfDeclaredBlobIsFatalRatherThanReadAsAbsent`.

**W-6 — `map_persistent` declines WITHOUT calling the applier.** Two reasons and the second is
the finding: the answer is a host pointer, which cannot cross; and
`MGPWireRec_MapPersistent`'s payload is a bare `MGPHandleOnly`, so **the record carries neither
the `size` nor the `seedBytes` that `MGPipeApplyMapPersistent(handle, size, seedBytes)`
takes**. R-6's constant decline is what makes that not matter in P5. See §6.

**W-7 — the decoder writes NO `RingControl` field.** It keeps its own `AppliedSeq()` tally
instead. See §8.1: this started life the other way round and s1's landing corrected it.

**W-8 — the three blob length cross-checks that were inert are now computed, not trusted.**
`CreateRenderState` against `MGPipePipelineChunkBlobBytes(desc.ChunkMask)`, `SetDynamicState`
against `MGPipeDynamicChunkBlobBytes(dyn.ChunkMask)`, `CreateSamplerState` against
`sizeof(SamplerParameters)`, `SetResidualValueState` against `sizeof(ResidualValueBlock)`. The
expected length is derived from a field the record itself carries, so it is a check and not a
restatement. `CreateVertexElements`' and `ResourceSubData`'s remain the applier's
(`PipeApply.cpp:1990-1999`, `:702`) — arming `Size` is what makes those live for the first
time, which is the whole point of rule A.

## 5. What the other packages have to know

**v1 — three things.**
1. `PipeWireDecoder` **writes no `RingControl` field at all** — `appliedSeq`'s single writer is
   s1's `SessionConsumer::ApplyOne`. `PipeWireDecoder::AppliedSeq()` is the decoder's own
   tally, kept *beside* the session's on purpose: the two must agree after every record, and
   that comparison is what makes R-9's batching ban checkable rather than merely stated. Whoever
   publishes `retiredSeq` should publish it together with `appliedSeq` in P5, because nothing in
   this phase borrows a ring slot into the GPU timeline — the day something does, that is the
   line that splits. **`retiredSeq` is the one watermark this package reads**: the encoder's
   SEG_STAGE reclaim is gated on it, so a `retiredSeq` left at 0 ends the first
   `MOBILEGL_IPC_STAGE_MB` of staging in `Fatal{RingOverrun, "SEG_STAGE"}`.
   **And do not attach a `RingConsumer` to `RingCursorSet::Stage`** — §10/M2.
2. **`Wire::WireVerbSink` is yours to implement.** Contract §7's five class-B verbs — `Clear`,
   `Blit`, `ReadPixels`, `DrawVbo`, `Present` — have **no `MGPipeApply*` entry point at all**
   (the 37 that exist are the object and state families), so the codec decodes, validates and
   hands over a checked argument list, and the backend call is the server's. With no sink
   installed those five arms return `false`. `OnReadPixels` is handed the record's seq and the
   `ReplySink` because P5 blocks on `read_pixels` and the pixels come back in the reply slot.
3. The server role calls `SegmentTable::InstallProcessResolver()` **before the apply thread
   starts** and `UninstallProcessResolver()` **after the join**. A second install is Fatal.

**s1 — two things.**
1. The codec owns no `Doorbell` and must not: `PipeWireEncoder::Publish()` release-stores the
   two ring heads and `submittedSeq` and stops there, so a unit case can drive
   encoder → ring → decoder with no transport. **Ringing the consumer doorbell after Publish is
   the session's line**, and it is publish-then-notify, never the other way round.
2. `CapsAbiFingerprint()` is ready for `Hello`/`Welcome`. It mixes
   `sizeof(DynamicBackendParameters)`, `sizeof(MGPCaps)`, `sizeof(GLFunctionsTable)`, both
   table dimensions, both codec versions, `MGPWireOp::kOpCount` and the git stamp — the stamp
   because two builds with the same sizes can still disagree about a field order, which no
   `sizeof` can see.

**c1 / b1 — three things.**
1. `EncodeRecord` cross-checks the tails you hand it **against the counts in your own
   payload**, so a `Count` that does not match the bytes is Fatal on the producing side. A tail
   whose count is zero may be omitted entirely.
2. `StageBytes(bytes, 0)` is **Fatal**, not an empty ref: "declared no blob" and "declared an
   empty blob" must not be spelled the same way on a wire. Stage first, then fill the payload's
   `MGPBlobRef` from what it returns — the encoder's honesty pass refuses a payload whose
   blobrefs were not filled that way.
3. **`MaxRecordBytesSeen()` is on the encoder; publishing it into `PipeStats` is b1's line**
   (`MG_Util/Metrics/PipeStats.*` is b1's file, so w1 did not touch it). R-10's number goes
   into MEASUREMENTS from there.
4. **The codec preserves declared padding byte for byte.** One line, because the next package
   to put a field in a pad will want it without reading the code: `EncodeRecord` `memcpy`s the
   whole payload struct and the decoder hands it to the applier by reference; nothing is built
   field by field, no pad is normalised, and there is no assertion anywhere that a pad is zero.
   The only `memset`s are strictly OUTSIDE `sizeof(Payload)` — the record's own alignment
   padding and the gaps between tails, which are zeroed so a record is a function of what it
   declares rather than of whatever the ring last held. Pinned by
   `EveryPayloadByteCrossesIncludingTheOnesSpelledPad`, which stamps the whole struct with a
   recognisable byte, writes only the fields the decoder validates, and `memcmp`s the lot — it
   **names no pad member**, so it will not stop compiling the day someone claims one.
   *The one place a pad is minted rather than preserved:* `StageBytes` returns a brand-new
   `MGPBlobRef` with `Pad0 = 0`. A phase that puts a field in `MGPBlobRef::Pad0` must set it
   **after** `desc.Blob = StageBytes(...)`, not before.

**t1 — one thing.** `MOBILEGL_IPC_AUDIT=1` arms the `0xDD` fill and
`PipeWireDecoder::PoisonedStageBytes()` is what proves it ran. A lane that sets the knob and
asserts nothing has not exercised R-2.5.

## 6. Debt this phase leaves, named

1. **`map_persistent` has no carrier for `size` or `seedBytes`** (W-6). The phase that lands a
   real one needs an `MGPipeTypes.h` payload change — c0's file — before it can even call the
   applier. R-6 hides this completely in P5.
2. **`SetShaderBuffers` (38) and `SetStreamOutputTargets` (39) still have no consumer.** Both
   are on BRIEF §4's exclusion list, so inventing one would be a semantics nobody can test this
   phase. What they *do* have now is their tail arithmetic — including the
   `HostSpanCount is 0 or Count` rule that keeps the two arrays index-aligned — so the phase
   that implements them inherits a validated record rather than a validation problem.
3. **`GetCaps` (1) decodes to `false`.** The snapshot is built from the server's live backend
   and posted by `ServerSession::PublishCapsSnapshot`; the codec validates the record's two
   blobrefs and declines rather than inventing a caps source.
4. **FOUR counts have no GL constant bounding them**, not two (review m6):
   `ResourceSubData.RegionCount`, `DrawVbo.NumDraws`, `SetShaderBuffers.Count` and
   `SetStreamOutputTargets.Count`. All four are bounded only by the record fitting the ring —
   the first two through `Fatal{RingOverrun}` naming R-10 and the integrator, the other two
   through `MGPipeWireRecordLayout`'s 32-bit `record.Size` bound and then `MaxRecordBytes()`.
   Every other count is held to `kMGPipeMaxVertexAttribs` / `kMGPipeMaxTextureUnits` /
   `kMGPipeMaxImageUnits` / `popcount(Mask)`.
5. **`MGPipeApplyWireRecord`'s `remaining` parameter is now inert on the split path**: the
   decoder passes `size` for it, because `RingConsumer::Pop` has already proved the record fits
   what the producer published. It is kept because the signature is the generator's.
6. **`MG_Pipe/MGPipeHostSpan.h` was not touched.** The resolver install point named in the
   ownership table is exercised from `SegmentTable::InstallProcessResolver()`; adding anything
   to that header risks a pull-build symbol for no gain (G1).
7. **No chunking** (R-10), and no compression in `CapsCodec` beyond the sparse tables.
8. **`SEG_STAGE` bytes staged for a record that is never encoded are never reclaimed.** The
   mark is taken in `EncodeRecord`, so a caller that stages and then abandons leaks staging
   until the ring is rebuilt. Nothing does that today (staging is always immediately followed
   by the record that names it), and making the allocator transactional would need a
   scope object the c0 signatures do not have — so it is written down rather than guarded.

## 7. Where I think the contract or the brief is wrong

1. **`PipeWire.inc:37`'s description of `MGPWireRecHeader::Flags`** — see §3. This is the one
   I want changed.
2. **BRIEF §5 w1 says "71 条的 encoder".** The encoder is *generic by opcode*: one
   `EncodeRecord` plus `StageBytes`, held to a per-opcode layout and a per-opcode honesty pass.
   A 71-way encoder switch would be 71 places for a caller to be wrong instead of one, and c0's
   signature (`EncodeRecord(op, payload, payloadBytes, tail, tailBytes)`) already says so. What
   *is* 71-way is the decoder, because each arm names a different applier.
3. **Contract table 1 row 3 says `CreateShaderState` is "seven independent runs".** It is one —
   see W-1. The row's own evidence (the archive codec, and the applier taking two typed
   pointers) is what makes it one.
4. **The brief's R-2.3 lists four Fatal arms; there are five.** The half-declared blobref
   (W-5) is a real shape, it is what every monolith emitter writes today, and reading it as
   "absent" loses bytes silently.
5. **Contract §0 rule A says a content record "must set `Seg` … `Offset` … and `Size`".** True,
   but the predicate *"is this a content record"* is per-op and lives in the payload, which is
   why `CheckBlobIsHonest(op, blob, segments)`'s signature cannot express it. Not an error in
   the contract, but the split into two functions is worth recording so nobody looks for arm 2
   inside the first one.

### 8.1 s1 — the single-record cap, and `appliedSeq` has one writer

> **Superseded in part.** s1's own fix round reversed the cap back to **4 MiB** — `MOBILEGL_IPC_RING_MB` now names the ring and the segment adds a page on top, so the contract is true as written. The reasoning below stands and the numbers are corrected; §10 records the reversal. Part (b), `appliedSeq`, is unaffected.

**(a) The 2 MiB cap needed NO change, and that is the finding.** `CONTRACT-P5.md §5` and
`Config.h` both say 8 MiB of `SEG_CMD` caps a record at 4 MiB; s1 found the 4096-byte control
page at the head of the segment, which makes the power-of-two ring 4 MiB and
`RingProducer::MaxRecordBytes()` **2 MiB**. Nothing in the codec had to move, because **every
comparison already went through `RingProducer::MaxRecordBytes()` and `Capacity()` at runtime**
— there is no constant anywhere in `PipeWireCodec.{h,cpp}` derived from `MOBILEGL_IPC_RING_MB`,
and the two Fatal messages print the live numbers. The unit case now says so in its header.

**And R-10's headroom is much larger than the 2 MiB figure suggests, for a structural reason
worth stating.** `CreateShaderState` is **not** the record most likely to approach the cap — it
is one of the *smallest*. Its record is `8 + sizeof(MGPProgramDesc)` = **200 bytes** whether
the archive is one kilobyte or one megabyte, because R-10's own rule sends every blob through
`SEG_STAGE` and leaves `{Seg, Offset, Size}` in the record. Pinned by
`ABigProgramArchiveDoesNotGrowItsRecordAtAll`: a 32 KiB module archive produces a 200-byte
record and 32 KiB of staging. The archive's bound is `MOBILEGL_IPC_STAGE_MB` (32 MiB) with its
own named `Fatal{RingOverrun, "SEG_STAGE"}`, not the record cap.

What *can* approach 2 MiB is a **var-tail**, and only two of them are unbounded by a GL
constant:

| row | worst case | vs the 4 MiB cap |
|---|---|---|
| `SetSamplerViews` / `SetShaderImages` | 192 units × 24 B + 24 = **4 632 B** | **0.11 %** |
| `BindSamplerStates` | 192 × 8 + 24 = 1 560 B | 0.04 % |
| `SetVertexBuffers` | 32 × 32 + 32 = 1 056 B | 0.03 % |
| `SetVertexAttribDefaults` | 32 × 24 + 16 = 784 B | 0.02 % |
| `SetFramebufferState` (largest fixed payload) | 312 B | 0.007 % |
| **`DrawVbo`** | `NumDraws` × 12 B — **no GL constant bounds it** | 4 MiB ⇒ ~349 000 draws in one `glMultiDraw*` |
| **`ResourceSubData`** | `RegionCount` × 40 B — likewise | 4 MiB ⇒ ~104 800 regions in one record |
| **`SetShaderBuffers`** / **`SetStreamOutputTargets`** | `Count` × 24 B (+ 32 B or 4 B) — likewise | caught by the 32-bit `record.Size` bound and then by `MaxRecordBytes()` |

So **nothing in the bounded part of the catalogue comes within 900× of the cap**, and I do
not think P5 has to chunk. **Four** rows are unbounded by any GL constant, not two (review m6):
`DrawVbo.NumDraws`, `ResourceSubData.RegionCount`, `SetShaderBuffers.Count` and
`SetStreamOutputTargets.Count`. All four are caught — the first two by
`Fatal{RingOverrun, "<call>"}` naming R-10 and the integrator, the last two by the 32-bit
`record.Size` bound in `MGPipeWireRecordLayout` and then by `MaxRecordBytes()` — so all four
are loud rather than silent, but only the first two say R-10 in the message. **A real measurement on OpenRA is still owed** — `MaxRecordBytesSeen()` is the
counter, and publishing it into `PipeStats` is b1's line, so the number reaches MEASUREMENTS
from there, not from here.

**(b) `appliedSeq` needed a real change** (`c1b5c2a0`). The decoder used to publish both
`appliedSeq` and `retiredSeq` after every record, on the reasoning that the decoder is the half
that knows when a record's staged runs stop being read. s1 owns that watermark and has exactly
one writer, so the decoder now writes **no** `RingControl` field and keeps a private tally.
That is the better shape anyway: two counts that must agree make R-9's batching ban
*checkable*, which one count could not, and `TheDecoderWritesNoRingControlFieldOfItsOwn` plus
`AppliedSeqAdvancesByExactlyOnePerRecordAndIsNeverBatched` are the two cases. The test fixture
now plays the session's role, which is also more honest about where the line is.

### 8.2 b1 — `MGPSubData::Pad0` is no longer padding

**No code change was needed; a test was.** The codec `memcpy`s whole payload structs and never
constructs one field by field, never normalises a pad and never asserts one is zero, so b1's
`HasLiveHostWrites` bit crosses intact — see §5's item 4 for the one-line statement, which is
what the next package to claim a pad should read.

What was missing was a **test that could see it**: the round trips compared named fields, and
a codec that zeroed a pad would have gone green through every one of them. `52bf9acc` adds
`EveryPayloadByteCrossesIncludingTheOnesSpelledPad` and `ResourceDescPadsCrossToo`, which stamp
the whole struct and `memcmp` the payload as it lands in `SEG_CMD`. Both deliberately **name no
pad member**, so b1's rename will not break them — a case that said `Pad0` would stop compiling
on exactly the day it became load-bearing.

This is also the second time in one phase that a "pad" turned out to be a field: P5 itself put
`HasRespecifiedLevel` / `RespecifiedUploadTarget` / `RespecifiedLevel` into `MGPResourceDesc`'s
two pads (contract table 1 row 19b). **Two for two is a pattern, not a coincidence**, and a
codec is the wrong layer to have an opinion about which bytes are meaningful.
