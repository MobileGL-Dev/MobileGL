## 2. ID-42 — CONFIRMED, with evidence, and what the fix is

### 2.1 The provisional diagnosis, checked line by line

**Reproduced first**, exactly as asked:

**Claim 1 — "the assertion never ran in the push build (tracker unavailable → early return)".
CONFIRMED.** `PersistentMapPeek.cpp:26` compiles the tracker half only when
`MGITEST_PERSISTENT_MAP_TRACKER` is defined, and `MG_IntegrationTest/CMakeLists.txt:1832-1843`
defines it **inside `if (MOBILEGL_BUILD_DISAGGREGATED)`**. A push build never compiles `MG_Remote`,
so `PersistentMapTrackerAvailable()` is false, and the old `AssertMembership` recorded
`"unavailable"` and returned at its first line. The seven entries went red the first time the
assertion ran at all.

**Claim 2 — "on the split build's monolith lane the map is ADOPTED (tier T1)". CONFIRMED, and the
tier name is the only thing I would correct.** Direct evidence, read from the production peek:

```

    --gtest_output=xml:...
  <property name="persistent_map_arm" value="adopted"/>
```

The mechanism is `PipeApply.cpp:2005`: R-6's decline is
`if (MG_Config::Transport != Monolith && AdoptTierIsEmulate()) return nullptr;` — **ANDed with the
transport**. Under `MOBILEGL_TRANSPORT=monolith` the decline is skipped, `g_resourceOps->MapPersistent`
mints, `BufferObject.cpp:856` calls `AdoptPersistentMap`, and `IsBackendPersistentMapped()` is true.
So the store is adopted by the ordinary monolith path rather than by an adopt *tier*: `AdoptTier` is
still 2 the whole time. "Tier T1" in ID-42 should read "the monolith mint" — the conclusion is
unaffected, but the distinction matters for the next claim.

**Claim 3 — "`IsLivePersistentMap` answers false on its `IsBackendPersistentMapped()` row by
design". CONFIRMED verbatim**, `PersistentMapTracker.cpp:40-58`:

```cpp
Bool PersistentMapTracker::IsLivePersistentMap(const BufferObject& buffer) {
    if (!buffer.IsMapped()) return false;
    // ... At tier T2 this arm is unreachable - MapPersistent declines - but
    // the predicate must still read the chain, not the tier ...
    if (buffer.IsBackendPersistentMapped()) return false;
```

**Claim 4 — "the membership claim is only true on the emulated arm". CONFIRMED.** The set is the set
of maps the client still has to PUSH; an adopted store's bytes are already in coherent GPU memory
and there is nothing to ship, so it must *not* be a member.

### 2.2 The fix

`PersistentCoherentMapScenario.cpp`: `AssertOrRecordArm` now **remembers** the arm it observed in
`m_observedArm` (a three-state `ObservedArm{NotLookedAt, Adopted, Emulated}`), and `AssertMembership`
expects `live == (arm == emulated)` from **that same peek** — not a second one, which would be a
second question that could straddle a change. `NotLookedAt` records and does not assert, because
"could not look" is not "it was emulated" (`PersistentMapPeek.h`'s own rule); a lane that *declares*
an arm has already been skipped by `AssertOrRecordArm` in that state. The failure message names both
directions and points at the unit case for the arm-independent half.

`MG_Test/Buffer/SplitBufferTest.cpp`: the arm-independent statement is pinned by a new unit case,
**`SplitBufferSet.TheAdoptedArmIsNotAMemberAndItIsTheChainRowThatSaysSo`** — not by an integration
entry, because an integration entry only ever sees whichever arm its driver and transport hand it,
which is precisely how the old assertion came to state the emulated arm's property as universal.

The case produces both arms and compares them:

- a **declined twin** with no backend ops: not adopted, and a member;
- an **adopted** buffer produced by the *production* path — a `BufferBackendOps` table whose only
  live member is `AcquirePersistentMap`, installed for exactly one `AcquireMemoryRange` call with
  `Transport` flipped to `Monolith`, because `PipeApply.cpp:2005` means there is no other way to
  reach a mint in this build. The case never sets a flag by hand: with the production adoption
  deleted the buffer is simply not adopted and the case fails on its own `ASSERT_TRUE`, which is
  R-16's rule.

The predicate is then asked with the tier back at **T2 / `InProcess`** — the configuration in which
R-6 says every acquisition declines — and must still answer "not a member". Two asserted
consequences follow: `NoteMapStateChanged` (the production set-maintenance entry point, not a
member read) refuses to enrol it, and `PushPersistentMapsBeforeVerb()` ships the declined twin's
4096 bytes and nothing else.

What I did **not** claim: the case does not pin `PushBlocksFor`'s re-check of a *stale* member,
because that state is not reachable through production paths on this tree —
`NotePersistentMapStateChanged` early-returns unless `PushIsArmed()` (`BufferObject.cpp:430`), and
`EnsureGpuResidentStorage` refuses a mapped buffer outright (`:783`). The re-check stays
belt-and-braces and unpinned; saying so is better than a case that pretends to drive it.
