## 3. Rulings I made that the brief did not

Every one is also in `CONTRACT-P5.md §6`, with what would overturn it. Here, only the ones a
package will trip over.

**3.1 `CallMask` bits 32..47 carry the consumer mask.** R-8 says the client's liveness gates
read the `CallMask` mirror instead of `MGPipeGetResourceOps()`. But `CallMask` as declared has
only the nine `MGPCapBit` feature bits and **no per-family bit**, so R-8 was not implementable
as written — c1 and b1 would each have invented one. Ruling: bits 0..8 stay `MGPCapBit`; bits
32..47 are `(serverConsumedSubsystems & 0xFFFF) << 32`. Constants and the fold/test helpers are
in `MG_Remote/CapsCodec.h`; `CapsCodec.cpp` asserts the block does not collide with the cap bits
and that P4a's `0x1fff` fits. *Overturned by* a decision to carry a second schema field instead.

**3.2 `ResourceFlushRange` carries no bytes at all** — a third answer, not either of R-13.2's
two. The ladder it drives rewrites its range *"from the authoritative shadow"*
(`Managers.cpp:1047-1076`), and under R-11 the authoritative shadow is server-owned, so
`resource_subdata` is **already** the only way bytes reach it. A blobref would be a second,
forgeable way to say the same thing. *Overturned by* evidence that tier-1 `INVALIDATE_RANGE`
needs bytes and range in one record — impossible while the verb barrier holds; **revisit when
the barrier retires for the buffer family.**

**3.3 `ResourceRespecify` has a SECOND uncarried companion and the brief does not mention it.**
`const MGPRespecifiedLevel* level` (`PipeApply.h:792-795`) is the **scope** of the redefinition
and `MGPResourceDesc` cannot express it. Without a carrier, every per-level `glTexImage2D` in
OpenRA silently takes the whole-resource arm and drops every pending upload — precisely the
texel loss the server-side set exists to prevent. Ruling: two named fields in the **existing
pads** — `Pad1` (4 B) becomes `{Uint16 RespecifiedUploadTarget; Uint16 RespecifiedLevel;}` and
one byte of `Pad0` becomes `Uint8 HasRespecifiedLevel`. Zero size change,
`MGP_ASSERT_POD(MGPResourceDesc, 88)` does not move. **I ruled and specified it; I did not
implement it** — `MGPipeTypes.h` is not c0's file. It is coupled to `PipeFields.def`, which *is*
mine (pads are excluded from field lists, so the two named members must be added there or
`--check` fails). **Integrator: land this before w1 encodes the record.**

**3.4 R-13.3 confirmed, with the cost that makes it obvious.** `MGPBlobRef` is 24 bytes;
`MGPResourceDesc`'s two pads total **6**. A blob member takes the struct 88 → 112 and moves the
POD assertion. The recommended route reuses `MGPipeForEachSubDataRecordRange`, which is already
chunked and already acceptance-gated, and **the texture path already does exactly this** —
`TextureEmit.h:1137` passes `nullptr` and relies on a following upload. So the ruling
generalises today's texture behaviour to buffers rather than inventing anything.

**3.5 Table 1 is 23 rows.** The brief's 19 and `scout-premortem:§3`'s 19 are **different lists**;
the four only the premortem carries — `MapPersistent`, `ResourceReadback`, `ReadPixels`,
`GetTextureImage` — are exactly the server → client ones. A phase that omits them discovers in
week three that it never decided where readback pixels land. Ruling for `ReadPixels`:
**destination is always `SEG_REPLY` in P5**, so `MGPReadbackInfo` gains no `Seg` field.

**3.6 `tableSlotMask` is deleted, not renamed** (R-8 allowed either). Decisive: `GLFunctionsTable`
has **69** function-pointer slots and `ulong` is 64 bits — the field cannot address the table its
own comment names, and never could. `maxComputeWorkGroupCount`/`Size` and
`prefersCpuXfbPrimitiveAccounting` go with it.

**3.7 The persistent-map census is 21 sites, not 20**, and `DirectGLES.cpp:361`
(`ResolveIndirectCommandBytes`) is in the set. `MEASUREMENTS.md:111` says 20 and
`Managers.cpp:5047-5048` says eleven Espryt; both are exactly one low and the missing one is
Espryt's. A shared helper that reaches a persistently-mapped range can read stale bytes exactly
as a draw site can. **`ARCHITECTURE.md:290`'s cited "§5.7" attribution table does not exist in
the tree** — b1 should not go looking. Correcting `MEASUREMENTS.md:111` is b1's line.

**3.8 `MOBILEGL_BUILD_DISAGGREGATED` implies `MOBILEGL_PIPE_PUSH`.** The split path decodes into
the MGPipe applier and `PIPE_PUSH` is what compiles the applier, so
`-DMOBILEGL_BUILD_DISAGGREGATED=ON` alone used to configure cleanly and fail at link — a shape
indistinguishable at the CMake level from a legitimate transport-only build.

**3.9 The two doorbell accessors stay off `ITransport`.** They are on `InProcessTransport`
today (`InProcessTransport.h:64-68`). Ruling: the **session** owns the pair and hands out
references, so `ITransport` stays the dumb control-plane interface its own header describes and
`SocketTransport` does not grow two accessors with no natural home. Deciding this in P6 would
mean re-laying one package's call sites.

**3.10 `gMGPipeSegmentResolver` is installed by the SERVER role only.** It is one process-wide
non-atomic inline variable (`MGPipeHostSpan.h:47`), so it cannot be per-role — and under R-2 the
client never resolves a span anyway, it only ever writes `Ptr = nullptr`.
`SegmentTable::InstallProcessResolver()` asserts if one is already installed.

**3.11 `DrawVbo`'s host span stays in the variable tail.** `MGPipeTypes.h:1221-1224` defers the
fixed-head-versus-tail question to P5. There are no per-draw byte histograms yet, so moving it
would be a wire-format change with no measurement behind it. Keep.

**3.12 Silent `MOBILEGL_TRANSPORT` in a non-disaggregated build is accepted and unfixable at
runtime.** A complaint would have to live in the unconditional part of `ConfigLoader`, which
resizes a pull-build symbol and breaks G1. The guard is therefore t1's build-level `nm` check,
and it is written into the contract so nobody re-litigates it.

## 4. The 18 split-build unit aborts — root cause and disposition

**Disposition: FIXED here, by c0, in one test-local commit. Nothing is left red, and none of it
is p1's.**

The brief's leading hypothesis — a `PipeInputs` poison read hitting
`Fatal{UnmigratedPipeInput, "<Field>@<none>"}` — is **refuted**. `MG_Test/ScopedPipeVerb.h` is
not involved at all.

All 18 are `Fatal{ProtocolCorruption}` trip wires in `PipeApply.cpp` that **the tests
deliberately provoke and expect**, e.g.

```
MGPipe: Fatal{ProtocolCorruption} create_vertex_elements {slot=5, gen=2}: the declared blob
length is not the byte length the two counts describe (attributes=3, bindingPoints=2, that
describes 104 bytes, blob declares 103)
```

`MOBILEGL_PIPE_POISON` **is** derived from `MOBILEGL_BUILD_DISAGGREGATED`
(`PipeInputs.h:20-26`, exactly as the brief says) — but what it arms here is a *second* consumer,
`PipeApply.cpp:42-52`, which flips 32 trip wires from `MGLOG_E` to `MGLOG_F` + `abort`. Each of
the seven test files has a two-armed helper keyed on `#if MOBILEGL_PIPE_POISON || MOBILEGL_PIPE_VERIFY`
that picks between "fork a child and expect it to die" and "run in process and read the log".

**None of those seven TUs included `<MG_Backend/MGPipe/PipeInputs.h>`, the only header that
defines the macro.** So the token was undefined, the `#if` silently read 0, and they compiled
the non-aborting arm while `PipeApply.cpp` — which does include the header — compiled the
aborting one. Invisible in a push build (POISON really is 0) and in a verify build
(`-DMOBILEGL_PIPE_VERIFY=1` is on the command line); **`MOBILEGL_BUILD_DISAGGREGATED` is the one
arming condition that lives behind the header**, so `build-split` is the first configuration
that could ever expose it.

Fix: one include per file, matching what the two sibling files that get it right already do
(`RenderStateSpansTest.cpp:63`, `PipeInputsTest.cpp:34`), each with the six-line note explaining
why. Plus one latent guard correction that the same invisibility was masking:
`ResourceEmitTest.cpp`'s `TheLiveHostWritesWireFiresOnTheCallAPersistentMapProducerWouldSetItOn`
guarded itself with `#elif !(MOBILEGL_PIPE_POISON || MOBILEGL_PIPE_VERIFY)` while
`PinNoLiveHostWrites` is `#if MOBILEGL_PIPE_VERIFY` **only** (`PipeApply.cpp:838-853`) — so in a
split build the wire genuinely is compiled out and the case must skip. Corrected to
`#elif !MOBILEGL_PIPE_VERIFY`; verified **SKIPPED in push, SKIPPED in split, OK in verify.**

**Why it is c0's and not p1's:** p1's artefacts are all correct as they stand. `PipeInputs.h`
derives the macro the way its own comment says it must; `PipeApply.cpp` consumes it correctly;
`PipeFill.cpp` and `gen_pipe_dirty_surface.py` are not in the path. The defect is entirely
consumer-side visibility in seven files under `MG_Test/Pipe/`, which are not p1's (t1 owns only
`MG_IntegrationTest/**`), and the fix introduces no new convention — that `MG_Test` →
`MG_Backend/MGPipe/PipeInputs.h` edge already exists twice in the same directory.

**One hardening left on p1's account, deliberately not taken:** if the integrator wants
`MOBILEGL_PIPE_POISON` to be unmissable, the derivation could move into a header every push TU
already sees (`MG_Pipe/MGPipe.h`), or `PipeInputs.h` could grow a tripwire for TUs that test the
macro without it. That changes a p1-owned header and touches every push TU's macro surface —
a much larger blast radius than a seven-line include for a defect the include closes completely.
**Filed as a p1 note; not done here.**

*(One caveat inherited, not introduced: running a whole fixed binary by hand — all cases in one
process — leaves some `FramebufferEmit`/`TextureEmit` fork cases red, because the parent has
already opened the log file and the child inherits a handle to the unlinked inode. That is the
limitation `RenderStateSpansTest.cpp:1034-1040` names; under ctest every case is its own process
and it does not arise.)*

## 6. Everything in the brief I believe is wrong or incomplete

Ordered by how much it would cost a package to discover it.

1. **R-13.3 covers only one of `ResourceRespecify`'s two uncarried companions.** §3.3. The
   `MGPRespecifiedLevel*` scope needs a carrier or OpenRA's per-level uploads are silently lost.
   **This is the one I most want the integrator to act on before w1 starts.**
2. **R-4's "69 slots" is `GLFunctionsTable`'s count; the table the client installs is 71.**
   `Present` is on the reduced path and `Present`/`SetSwapInterval` have **zero `MG_Impl` call
   sites** — they are reached through the EGL path, so an emit table built by mirroring GLImpl
   covers neither.
3. **R-4's predicted minimum set names `Flush`. There is no `Flush` slot, and `glFlush`/`glFinish`

### 8.2 Work item 1 — the carrier, landed

`MGPResourceDesc` (`MGPipeTypes.h`), exactly the §3.3 spec and nothing more:

- `Uint8 HasRespecifiedLevel` takes the **high byte of the old `Pad0`** (`Uint16 Pad0` →
  `Uint8 HasRespecifiedLevel; Uint8 Pad0;`);
- `Uint16 RespecifiedUploadTarget; Uint16 RespecifiedLevel;` take **all of the old `Pad1`**, in
  that order, so they are `MGPRespecifiedLevel` (`PipeApply.h:792-795`) byte for byte. Spelled as
  two `Uint16`s rather than as that type because `PipeApply.h` includes *this* header, not the
  reverse;
- **`MGP_ASSERT_POD(MGPResourceDesc, 88)` did not move**, and a new `offsetof` assertion pins the
  pair adjacent and in that order — the layout is the contract, not the field names.

**Five helpers, because three fields are one value.** `MGPipeRespecifyIsWholeResource`,
`MGPipeRespecifiedUploadTargetOf`, `MGPipeRespecifiedLevelOf`, `MGPipeSetRespecifiedLevel`,
`MGPipeClearRespecifiedLevel`. The two readers return 0 for a whole-resource descriptor rather
than whatever the pad held, so a misuse is deterministic; the writers set or clear the presence
byte *with* the pair so it cannot be left behind. An open-coded reader that forgets the presence
byte reads **level 0 of upload target 0 as a real scope**, which is the one wrong answer that
looks plausible — hence the helpers rather than a comment.

**No emitter or applier behaviour changed.** The producer is a later package's. What did change:

- `PipeFields.def` gains the three rows — **required, not optional**: the generator's cover check
  only excludes members literally named `Pad*`, so omitting them fails `--check`. Both directions
  verified as negative controls: dropping `F(HasRespecifiedLevel)` →
  *"member(s) with no F(...) in PipeFields.def: HasRespecifiedLevel"*; adding a name the struct
  lacks → *"F(...) name(s) that are not members: RespecifiedNothing"*. They are also real **G4
  comparands** now, which matters: a verify build that let the scope differ silently would be
  blind to the one field deciding whether a respecify drops one pending upload or all of them.
- `PipeApply.cpp` gains `PinWholeResourceRespecifyScope`, the `PinNoLiveHostWrites` shape
  (`:839-850`), called from `MGPipeApplyResourceRespecify` beside it. **Verify-build only**, and
  verified so: the `Fatal{PipeRespecifyScope}` string appears in `build-verify/libMobileGL.so`
  **once** and in `build-push` and `build-split` **zero** times. It pins that P5 builds only
  whole-resource descriptors, so the phase that wires the carrier cannot arrive unannounced —
  and in particular cannot land a descriptor saying "whole resource" while the still-live
  trailing `MGPRespecifiedLevel*` says "level 1".
- A standalone round-trip compile (value-init → whole-resource; set a cube face + level 3; read

**The "never blocks" contradiction is resolved in the contract rather than papered over.**
`MGPipe.h:49` says a reply-slot call never blocks; R-5 says these four answers are read
synchronously. Both hold, because **under the verb barrier the client is already waiting for
`appliedSeq >= mySeq` at that verb boundary and the reply is read inside that wait**. A
`kReplySlot` row therefore adds no block — it adds a read to a wait that was already happening.
The flag keeps its literal meaning; the barrier blocks, and the barrier retires per family, at
which point these four become genuinely asynchronous and the acceptance answer becomes a real
latency question. That is P9's account.

### 9.2 Item 2 — and the part of w1's finding that the tree contradicts

The generated comment said `Flags` was "MGPipeCallFlags of the call, for asserts and tracing",
which invited exactly the stamp w1 found. It now says what the field is: **ring framing flags,
and the two spaces are disjoint by translation, not shared.**

**But the finding as relayed is stronger than the tree supports, and I would rather correct it
than pin something false.** `RingProducer::Reserve` **masks `kRecPad` out** of a caller's flags
(`Ring.cpp`: `flags & ~kRecPad`). So:

| collision | status |
|---|---|
| `kVarTail` → `kRecPad` | **defended, one bit wide, one path wide.** A stamp through `Reserve` does *not* delete the record. A producer that writes the header itself — which is what a codec with its own header struct does, since these are the same eight bytes — loses the mask, and then `Pop` skips the record as a wrap filler. |
| `kHostSpan` → `kRecBorrowSlot` | **undefended.** The consumer believes the record borrowed a slot into the GPU timeline and retires it on `completedFrameSerial` instead of on apply. |
| `kReplySlot` → `kRecVarTail` | **undefended** — and after item 1 this now fires on **fourteen** rows rather than ten. |

So the real failure is not one dramatic disappearance: it is **a lifetime lie and a phantom tail
on every affected record**, plus a disappearance only on the path that bypasses `Reserve`. My
first version of the test asserted the dramatic version, and it failed — which is the system
working. The landed test pins all three shapes *including the masking*, so the one defence that
exists cannot quietly go away either.

**Enforcement, split by what each file can see.** MG_Pipe is below MG_Remote and may not include
`Ring.h`, so no generated `.inc` can hold a cross-enum assertion:

- **`gen_pipe.py` now reads `enum MGPipeCallFlags` out of `MGPipe.h`** rather than hard-coding
  it, and emits a value assertion per flag plus `kMGPipeCallFlagsAllBits == 0x3F`. A renumbering
  or a seventh flag is a build break, and — because the parse also feeds the existing
  unknown-flag gate — a flag added to the header no longer has to be added to the generator by
  hand, which is the copy that would have gone stale in exactly the case that matters.
- **`MG_Test/Wire/RingTest.cpp`** holds the cross-enum table: the one place in the tree that sees
  both enums, and built only under `MOBILEGL_BUILD_DISAGGREGATED`. Six correspondences, both
  totals (`0x3F` and `0x1F`), and a runtime half that demonstrates each of the three shapes.
