## 3. Rulings I made that the brief and the contract did not

### 3.1 `HasLiveHostWrites` rides `MGPSubData`, not `MGPResourceDesc`

**The brief names both pads (`:303` / `:1004`) and the natural reading is the descriptor's.
That reading does not work, and the reason is P4a's, not P5's.**

`MGPResourceDesc`'s only carrier is `resource_respecify`, and for a **buffer** the applier can
never classify one as metadata-only: `RespecifyRedefinesNoStorage` (`PipeApply.cpp:559`)
refuses `kMGPipeResourceTargetBuffer` **outright, as its first line**, and the comment above it
says why — that refusal is what makes ID-18 M4's "no reallocation ack" true *by construction*
rather than by a second suppression rule, because `glBufferData` at an unchanged size is the
canonical orphaning idiom and `glBufferStorage` is the one entry point allowed a synchronous
ack. So announcing a map on a descriptor would have dispatched
`g_resourceOps->Respecify(..., initialBytes)` — a full re-upload — **on every map and every
unmap**. That is precisely the "第一次推这个位就要一次假重分配" the brief warned about, and the
only way to register the bit as metadata on that carrier is to re-open the buffer exclusion,
which is a P4a contract the buffer family should not be re-opening for a flag.

`MGPSubData` has `Uint8 Pad0[3]`; one byte becomes `HasLiveHostWrites` and
`MGP_ASSERT_POD(MGPSubData, 72)` does not move. The fact is content-shaped anyway — "someone
may be writing these bytes without telling you" — and the carrier is the record the push
already emits, so the steady state costs **nothing**: the bit rides blocks that were going out
regardless.

**The falling edge is the part that needed a decision.** After an unmap there may be no further
content record for the buffer's life, and a record stuck at "live" reads draw-DIRTY for ever —
the mirror image of the C-1 regression, costing a re-upload per draw instead of losing bytes.
So `NotePersistentMapStateChanged` emits **one block** (`NotifySubData(0, min(size,
blockBytes))`) with the bit already cleared. The bytes are real and current — `ReleaseMemory`
has already landed the staged writes and called `NotifyFlushMappedRange` above it — and a
zero-length record was not an option (contract rule A). *Overturned by:* a decision to widen
`RespecifyRedefinesNoStorage` to admit metadata-only buffer respecifies, which would make the
descriptor carrier viable and remove the falling-edge record.

**This touches two c0-owned files** — `MGPipeTypes.h` (one pad byte) and `PipeFields.def` (one
`F(HasLiveHostWrites)`) — and is isolated in its own commit so the integrator can take or
reject it without unpicking anything else. `gen_pipe.py --check` is green without regeneration.

### 3.2 The four pins are lifted **for a split build only**, not deleted

`PinNoLiveHostWrites` becomes the no-op body under `MOBILEGL_PIPE_VERIFY &&
!MOBILEGL_BUILD_DISAGGREGATED`, and the `Managers.cpp` assertion takes the same guard. In a
monolith verify build nothing sets the bit and the wire is still the thing that would say so
if something started to — which is the whole value of the pin, and it survives the phase it was
written for instead of being consumed by it. The same is true of `frontend->IsMapped()`:
monolith keeps the frontend read, split does not have one to keep.

### 3.3 Row 1 (atomic counters) is deliberately WIDER than its backend twin

`SyncAtomicCounterBuffers` (`DirectGLES.cpp:578-583`) walks the GL bindings the **transpiled
program** declared; the client has the bindings but not that per-program list at the emission
point, so it marks every *touched* atomic-counter point. Over-approximating costs a readback
the narrowing channel then removes; under-approximating reads a stale counter and says nothing,
which is what every atomic-counter conformance case is. The asymmetry decides the direction,
exactly as `RespecifyRedefinesNoStorage`'s own comment argues for its width.

### 3.4 The image-unit walk sweeps, and is the one place P5 knowingly spends

The backend keeps a bitset of writable image-buffer units (`DirectGLES.cpp:2350-2352`) built
from its own `SyncImageTextureBinding`; the client has no equivalent, so it sweeps
`MAX_TEXTURE_IMAGE_UNITS` (192) with a null test per unit. Bounding it by
`MaxImageUnits` would have been a backend read, and a stale or absent backend object would
silently *shorten* the walk — the one direction a conservative set may not fail in.
**An image-unit high-water mark on `GLContext` is the obvious narrowing and belongs with P8's
binding-walk migration.** Recorded, not gated (2026-09-08 rule).

### 3.5 `glEndTransformFeedback`'s fence removal needed a second edit nobody named

Dropping the `~0ull` `ClientWaitSync` (`GL_Drawing.cpp:1367`) is safe for `glMapBuffer` — that
is what the flag is for — but `FixupGsStripCaptureOrder` (`GL_Drawing.cpp:1310-1338`) reads the
captured bytes back through `MappedData()` **in the same function**, so it was relying on the
fence without saying so. Under split it now calls `SyncGpuWrites()` on the buffer it is about
to read. Cost moves from every `glEndTransformFeedback` to the capture shapes that actually
need reordering.

### 3.6 `WritebackFromBackend`'s clear is whole-buffer only

The third state's exit is the writeback, but `FixupGsStripCaptureOrder` writes back **three
vertices at a time**, and a partial writeback is not an answer to a whole-buffer readback. The
clear is therefore `atOffset == 0 && data.size >= m_size`. Pinned by a unit case.

## 5. What I did not do, and why

- **No narrowing.** `ResourceTracker.h:587-592`'s `rangeCount == 1` assertion is untouched.
  A package that reads `:577-581` alone will think P5 owns it; it does not, it is P8/P9's.
- **`AwaitBufferWriteback` is a `return` and not a loop.** With no session — every unit lane,
  and a build-split lane running monolith — the emission *was* the application, synchronously,
  so a loop there would be a hang in exactly the configuration every gate runs. The real wait
  is the barrier's (`ClientSession::EmitAndWait`), because the reply-slot id **is** the record's
  seq; when s1/c1 land it, this function's body becomes their wait and not a second one.
- **The flush ladder's `hostBase` snapshot is specified, not implemented.** Taking the snapshot
  into `SEG_STAGE` is w1's encoder work. What b1 owes and has landed is the *decision* the
  snapshot makes unsafe: `InvalidateFlushAccessFor` refuses tier 1 whenever the map extent and
  the queued range disagree in either direction, so a snapshot that does not cover exactly the
  queued range costs a staging-ring copy instead of a silent clobber.
- **`ScopedDefaultUnpackState`'s six shadows, the `g_uploadRing` reset asymmetry and the
  unlocked `pendingRanges` / `pendingResidentWrites` probes** (scout §5.2-§5.4) are all still
  open. The third one is the live one: two threads make an unlocked emptiness probe of a
  container the apply side mutates, and `syncedChangeSerial` beside it is already an acquire
  load. It belongs to v1's thread work, not to the buffer family's shape.

## 8.1 B-1 — the cycle, and the test that could not see it

**Both halves fixed.**

**The cycle.** The diagnosis is right and it is the C-1 regression one layer down. The rising
edge of a write map emitted nothing, so for the one idiom the feature exists to serve - a
coherent persistent map behind a static VAO - the server never learned a host writer was live;
the only content record such a buffer produces is the push; the push runs inside
`EnsureBufferResourceForHandle`; a draw-clean answer **skips** that ensure
(`DirectGLES.cpp:691`) and then **latches** it (`:697`, and a coherent map bumps no mutation
epoch); and `PushPersistentMapsBeforeVerb()` has no caller. Draw 3 onward draws frame 1's bytes
for ever.

**Fix: option (b) — the rising edge publishes a real record.** One block, the same shape the
falling edge already proved affordable, so the server knows before the first probe. The probe
then answers dirty for every draw while the map is live, the ensure runs, the push runs, the
serial moves. `BufferObject.cpp`'s `NotePersistentMapStateChanged` carries the argument in full.

Options (a), (c) and (d) were considered and rejected: (a) leaves the last frontend read in a
function that has no frontend under spawn, i.e. it defers the actual deliverable; (c) has the
server read client state and is legal only under inproc, which is the shape R-2 exists to
forbid; (d) is c1's call site and b1 wiring the emit table would collide with the package that
owns it - and it would still leave the *probe* feeding itself.

**The test.** Rewritten to drive the production chain end to end and to touch the record only
by reading it: the resource subsystem is armed with an empty ops table (`MG_Test/Pipe`'s
`PushArm` shape), the buffer is constructed, respecified, mapped, written through the pointer,
pushed, unmapped - all through the ordinary frontend entry points - and the case reads
`MGPipeApplier().Resources[slot]`. The probe is handed a **null** frontend object, which is the
question a spawned server actually has to answer.

## 8.2 M-2 — `buffer_subdata_resident` clearing the bit

**Fixed**, one line in `MGPipeEmitBufferSubDataResident` beside the one in
`MGPipeEmitResourceSubData`. The assignment in `ApplyBufferWrite` stays an assignment - "a
content record emitted while nothing maps the buffer is how the state goes back to false" is
the rule - so the fix is to make the second emitter speak rather than to make the applier
merge.

One thing worth recording: under R-6 this path is **not reachable today**.
`MGPipeEmitBufferSubDataResident` is called only from `LandBytesIntoResidentStore`, which
requires `IsGpuResident()`, and at tier T2 nothing adopts. So it is a latent defect fixed for
P11 rather than a live one - which is also why no unit case drives it: there is no way to
reach it in a split build without first implementing T0/T1.

## 8.3 M-3 — `pmap` double-counts `stage-buffer`

**Fixed by amending the inventory, deliberately, and both entries say the same thing.**
The alternative - subtracting the push at the staging site - makes `stage-buffer` under-report
what the backend actually moves, which is the question that class exists to answer. So:
`stage-buffer`'s "NOT covered" clause is now "not covered IN A MONOLITH BUILD ... COVERED UNDER
SPLIT, AND DELIBERATELY OVERLAPPING", with the mechanism (a pushed block *is* an ordinary
`resource_subdata` at T2, so it reaches `Ops_H_SubData` and is staged), and
`persistent-map-push`'s entry now says "DOUBLE-COUNTED WITH stage-buffer, deliberately ...
adding them is wrong". The inventory is contract and it now describes the build it is read in.

## 8.4 M-4 — `MOBILEGL_IPC_PERSISTENT_BLOCK_KB=0`

**Fixed.** `blockBytes == 0` now returns before **either** edge emits, so the knob turns the
whole mechanism off - state record included - and an unmap delivers nothing. The unit case is
extended to drive `ReleaseMemory` under the knob and pins the exact serial arithmetic: with the
push on, an unmap moves the change serial by **2** (the unmap's own `NotifyFlushMappedRange`
plus the falling-edge record); with the knob at 0 it moves by **1**. A whole-buffer ship would
have been indistinguishable from the correct case without that.

## 8.16 One thing the fix round changed about the shape, stated plainly

The rising-edge record means a write map now costs **one `resource_subdata` at map and one at
unmap**, split-only, on top of the per-validate-point push. On a 128 MB streaming arena that is
two 64 KiB records per map/unmap pair, which is noise beside Phase 1's whole-span push - but it
is new traffic and it is the price of the probe not feeding itself. Phase 2's dirty bits should
subsume both: once the server can see which blocks moved, "a host writer is live" stops being a
separate announcement.

The reviewer's option (d) - wiring `PushPersistentMapsBeforeVerb()` at the validate point - is
still the right long-term shape and is still c1's call site. When it lands, the rising-edge
record becomes redundant for the *persistent* case (though not for a plain write map, which
emits no push at all) and should be re-examined rather than inherited.
